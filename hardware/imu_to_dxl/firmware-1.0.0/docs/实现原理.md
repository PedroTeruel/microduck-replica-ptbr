# Princípios de implementação

Este documento descreve o projeto interno do firmware (v1.0.0) da placa IMU para servo Feetech FT-SCS: máquina de quadros do protocolo, prevenção de colisões na ordem do SYNC READ, camada física half-duplex, fluxo de dados do IMU e mapa de registradores. Serve como referência para portar, desenvolver e diagnosticar o firmware.

---

## 1. Objetivo e arquitetura geral

### 1.1 Objetivo

- Hardware: STM32G031F8P6 (Cortex-M0+ a 64 MHz, 64 KB de Flash / 8 KB de RAM) + IMU de seis eixos LSM6DSV16X.
- Papel: dispositivo **escravo (ID=200)** na linha de barramento único Feetech FT-SCS, compartilhada com os servos Feetech (IDs 2, 3 etc.), a 1 Mbps, 8N1 e half-duplex.
- O contrato de dados acompanha o duck-control (lado RK3566) do GitHub `pollen-robotics/microduck`: três eixos do giroscópio e quaternion SFLP de ponto flutuante x/y/z (o host recupera w), lidos por SYNC READ a 50 Hz. Este projeto não executa os algoritmos de postura do Duck nem aplica rotação de instalação; isso é feito pelo duck-control upstream.
- Execução bare-metal, sem RTOS. Toda a lógica do protocolo roda no loop principal; a ISR apenas armazena bytes com timestamp em um buffer circular.

### 1.2 Organização dos arquivos-fonte

| Arquivo | Responsabilidade |
|---|---|
| `Core/Src/board.c` / `board_config.h` | Clock (HSI16 → PLL 64 MHz), barramento USART2, logs USART1, SPI1, base de tempo em microssegundos do temporizador, IWDG, transmissão half-duplex e buffer circular de recepção com timestamps |
| `Core/Src/protocol.c` / `.h` | Análise de quadros FT-SCS, checksum, distribuição de instruções e máquina de estados de respostas SYNC READ em ordem (~410 linhas, sem código de terceiros) |
| `Core/Src/control_table.c` | Visão de 256 bytes de registradores: empacotamento do snapshot do IMU, bloco de diagnóstico e comandos graváveis de marker/reinicialização do IMU |
| `Core/Src/imu.c` | Configuração do LSM6DSV16X, esvaziamento FIFO, análise da postura SFLP, amostragem a 120 Hz, detecção de falhas e recuperação automática |
| `Core/Src/main.c` | Agendamento do loop principal: recebe quadros → consulta protocolo → consulta IMU → logs; o tráfego do protocolo tem prioridade |
| `Drivers/LSM6DSV16X/` | Driver oficial da ST (somente definições de registradores) |

Fluxo de dados:

```
LSM6DSV16X ─SPI 2MHz─► imu.c FIFO/SFLP ─► imu_snapshot_t
                                              │ (leitura no loop principal, sem inconsistência)
USART2 ISR ─► buffer circular 256B (com timestamp µs) ─► protocol.c ─► control_table_read ─► quadro de resposta
                                              ▲
                                         proto_poll transmite quando o barramento está inativo
```

## 2. Implementação do protocolo FT-SCS

### 2.1 Formato dos quadros

```
Solicitação: FF FF ID LEN INST P_1 ... P_n        CK
Resposta:    FF FF ID LEN ERR  D_1 ... D_d        CK
             └cabeçalho┘ └ LEN = 1 (INST/ERR) + bytes de parâmetros/dados + 1 (CK) = comprimento total - 4 ┘
```

- Comprimento total do quadro = 4 + LEN bytes.
- Checksum (complemento de um byte):

  `CK = ~( ID + LEN + INST/ERR + Σ(parâmetros/dados) ) & 0xFF`

  Abrange os bytes a partir de ID, sem os dois bytes `0xFF` do cabeçalho.
- ID de broadcast = 254 (0xFE); IDs de escravo válidos = 1..252.

Vetores de validação (podem ser usados em testes próprios de portabilidade):

| Quadro | Bytes |
|---|---|
| Solicitação PING ID 200 | `FF FF C8 02 01 34` |
| Resposta PING (ERR=0) | `FF FF C8 02 00 35` (observe que o CK da resposta difere do da solicitação) |
| Solicitação READ 56/12 | `FF FF C8 04 02 38 0C ED` |
| Resposta READ de 12 bytes | LEN = 12 + 2 = 14 |

### 2.2 Conjunto de instruções

| INST | Nome | Parâmetros | Resposta |
|---|---|---|---|
| 0x01 | PING | Nenhum | Responde vazio, sem erro, somente a unicast; **PING em broadcast fica silencioso** (os servos do barramento respondem; o IMU não interfere) |
| 0x02 | READ | addr(u8), count(u8) | ERR + count bytes; count 1..128, addr+count ≤ 256; broadcast não é aceito |
| 0x03 | WRITE | addr(u8), data… | Retorna ERR em unicast; broadcast fica silencioso |
| 0x82 | SYNC READ | addr, count, id… (enviado em broadcast) | Cada escravo responde na ordem da lista |
| 0x83 | SYNC WRITE | addr, dlen, [id, dlen bytes]… | Executa silenciosamente, sem resposta |
| Outros | — | — | Descartados silenciosamente |

Não implementa Reg Write/Action/Bulk, não grava na Flash, e ID e baud rate são **fixos e não podem ser alterados** (gravar em 5/6 retorna erro de acesso). **Sem atraso de retorno**: a resposta é agendada imediatamente. Códigos de erro compatíveis com o significado Feetech: 1 RESULT, 2 INSTRUCTION, 3 CRC, 4 RANGE, 5 LENGTH, 6 LIMIT, 7 ACCESS.

Limites de tamanho dos quadros: `PROTO_MAX_READ=128`; LEN máximo aceito = 132 (LEN=130 para resposta READ de 128 bytes; LEN=132 para uma seção SYNC WRITE de 128 bytes). LEN maior é tratado imediatamente como ruído, para não engolir o restante do tráfego do barramento.

### 2.3 Máquina de estados de recepção (`proto_feed`, chamada para cada byte)

1. Procura dois `0xFF` consecutivos; aceita bytes FF iniciais excedentes; ID=0/255 reinicia a busca por ser inválido.
2. Ao receber LEN, calcula o comprimento total (4+LEN) e então acumula o quadro até esse tamanho; não procura cabeçalhos dentro dos dados.
3. Quando o quadro completo tem checksum válido, incrementa `rx_packets` e chama `execute()`. Se houver erro, incrementa `checksum_errors` e procura `0xFF` a partir do final do quadro para tentar recuperar o próximo cabeçalho embutido em um quadro curto incorreto (ressincronização).
4. Se o intervalo entre bytes ultrapassar 1500 µs (`PROTO_BYTE_TIMEOUT_US`), descarta o quadro incompleto e incrementa `receive_timeouts`.
5. **O timestamp é o instante em que a ISR recebeu o byte**, não o instante em que o loop principal o consumiu. Isso garante precisão temporal para decidir a ordem.

### 2.4 Regra de transmissão e barramento ocioso

A resposta é montada primeiro em `tx[]` e marcada para agendamento (`schedule_reply`). A transmissão real ocorre em `proto_poll()`:

- Quando `pending=1` (pronto para transmitir), só transmite se `rx_length==0` (não há quadro em recepção) e se o tempo desde o agendamento não exceder 2000 µs (`PROTO_REPLY_EXPIRY_US`); caso contrário, descarta esta tentativa e cede espaço no barramento.
- Se qualquer byte novo chegar enquanto `pending=1`, cancela imediatamente (`cancelled_replies++`): a atividade de outro dispositivo significa que o barramento deixou de estar livre.
- O loop principal esvazia o buffer circular de recepção antes de chamar `proto_poll`; isso é necessário para que as condições acima funcionem.

## 3. Respostas SYNC READ em ordem e prevenção de colisões (mecanismo central)

### 3.1 Problema: barramento compartilhado sem token de intervalo de tempo

Um quadro SYNC READ do FT-SCS contém a lista completa de IDs (por exemplo, `[2,3,200]`), visível a todos os escravos. As respostas devem seguir a ordem da lista sem colidir. Porém, o protocolo não tem um token explícito: o host não chama cada dispositivo individualmente, então cada escravo precisa decidir quando é a sua vez.

O firmware dos servos Feetech (versão 3.46 observada na prática) usa **previsão de intervalo**: não espera a resposta do dispositivo anterior terminar; começa a transmitir a própria resposta cerca de +180 µs após o início do quadro anterior. A placa IMU precisa coexistir com esse comportamento.

### 3.2 Máquina de estados de ordenação

O firmware percorre a lista de IDs e encontra sua posição i (distribuição SYNC READ em `protocol.c`, aproximadamente L260-263):

- **Primeiro item (i==2, o primeiro da lista)**: `schedule_reply(preceding=-1)` → `pending=1`; agenda transmissão imediatamente.
- **Item posterior**: registra o ID imediatamente anterior da lista e define `pending=2`. Depois, em `execute()`, **monitora o barramento**: somente ao receber um quadro válido, com checksum correto, do ID anterior é que muda de `pending=2` para `pending=1` (“o dispositivo anterior já transmitiu; agora é minha vez”).
  - Se não receber um quadro válido do dispositivo anterior dentro de 25 ms (`PROTO_TRANSACTION_TIMEOUT_US`), desiste desta rodada para evitar transmitir fora de hora.
  - Se, durante a espera, aparecer um novo quadro do host direcionado ao próprio dispositivo ou em broadcast, invalida a rodada atual (começou uma nova transação).

Uma lista válida de IDs precisa conter ao menos um ID, todos entre 1..252 e sem repetição. Uma lista malformada não gera resposta, mesmo que inclua o próprio ID.

### 3.3 Colisões observadas e regra obrigatória de ordenação

| Lista do host | Taxa de sucesso do IMU (30 rodadas) | Observação |
|---|---|---|
| `[200, 2, 3]` (IMU primeiro) | **3/30** | O servo começa cerca de +180 µs após o início do quadro IMU e colide exatamente com o byte de checksum do IMU |
| `[2, 200, 3]` (IMU no meio) | 30/30 | O IMU espera o quadro válido do ID 2 antes de responder |
| `[2, 3, 200]` (IMU por último) | 30/30 | Mesmo mecanismo, `preceding=3` |
| `[200]` (sozinho) | 30/30 | Sem servos subsequentes, não há colisão |

**Conclusão: o host deve colocar o ID 200 depois de todos os servos (penúltimo/último lugar, isto é, na posição final da lista) ou em um grupo separado; nunca na primeira posição.** Neste projeto, `bus_monitor.py` sempre usa `[servos..., 200]`, enquanto `imu_monitor.py` lista somente `[200]`.
(Uma tentativa anterior registrada no histórico de adicionar artificialmente um atraso de slot de 506 µs piorou o resultado e foi removida.)

### 3.4 Orçamento de tempo a 50 Hz (por que o tempo não é o gargalo)

A 1 Mbps, cada byte usa 10 bits (1 início + 8 dados + 1 parada):

- Solicitação SYNC READ (11 bytes para 3 dispositivos): aproximadamente 110 µs.
- Resposta com 12 bytes de dados (18 bytes no quadro): aproximadamente 180 µs por dispositivo.
- Ocupação total de uma rodada com três dispositivos: aproximadamente 110 + 3×180 = **650 µs**, somente **3,3%** do ciclo de 20 ms a 50 Hz.

Há ampla margem. A restrição real não é falta de tempo, mas a colisão elétrica provocada pela transmissão prevista do servo; por isso, a solução é ordenar os IDs e monitorar o barramento para ceder a vez, não comprimir os intervalos.

## 4. Camada física half-duplex

A placa usa um buffer de transmissão/recepção ligado ao barramento de fio único (consulte `board.c board_bus_send`):

- **PA1 = 1OE# (habilitação de direção, ativo em nível baixo):** vai a nível baixo antes da transmissão para acionar o barramento e a nível alto ao terminar para liberá-lo.
- **PB7 = RX_EN:** vai a nível baixo durante a transmissão para **suprimir o eco local** (evita receber o próprio quadro); PA3 mantém a recepção habilitada.
- Sequência de transmissão (com USART2 desabilitado na seção crítica protegida contra interrupção):
  1. Verifica novamente se não há atividade no barramento (`BUSY/RXNE/ORE/FE/NE/PE` todos limpos e buffer circular vazio). Se houver atividade, abandona a transmissão e incrementa `tx_busy_drops` (nunca sobrescreve um byte que esteja sendo recebido).
  2. PB7 suprime o eco → limpa a flag TC → PA1 vai a nível baixo.
  3. Escreve os bytes um a um em TDR e, no fim, **aguarda TC (transmissão concluída, incluindo o último bit de parada)**, em vez de TXE.
  4. Só então libera PA1 e restaura a recepção. Há um limite de tempo calculado pelo número de bytes; se expirar, incrementa `tx_timeouts`.
- Recepção: a ISR de USART2 coloca bytes um a um em um buffer circular de 256 bytes (potência de 2) com timestamp em microssegundos. Overflow incrementa `rx_overflows` sem sobrescrever dados antigos. Erros de hardware incrementam `uart_errors` e sinalizam `bus_fault`; então o loop principal chama `proto_reset_receiver()` para reiniciar a máquina de quadros.

Esta sequência — “montar quadro → aguardar ocioso → transmitir atomicamente → aguardar TC → liberar” — garante que a resposta completa apareça no barramento no tempo certo e que quadros recebidos e eco local não se contaminem.

## 5. Mapa de registradores (ID 200)

Todos os inteiros de vários bytes usam **little-endian**. A camada do protocolo controla os bytes 0..9 (somente leitura, valores fixos); os demais são empacotados sob demanda por `control_table`.

### 5.1 Identidade e configuração (0..9)

| Endereço | Comprimento | Conteúdo |
|---|---|---|
| 0..1 | 2 | Modelo 0x4D44 (little-endian: 44 4D) |
| 2 | 1 | Versão do firmware = 1 |
| 5 | 1 | ID = 200 (fixo) |
| 6 | 1 | Código de baud rate = 0 (código Feetech 0 = 1 Mbps, fixo) |
| 9 | 1 | Atraso de retorno = 0 (resposta imediata) |
| 3,4,7,8 | — | Reservado, leitura retorna 0; toda a faixa 0..9 é somente leitura |

### 5.2 Bloco rápido a partir do endereço 56 (mesmo endereço do bloco de estado do servo; SYNC READ 56/12 é central)

| Endereço | Comprimento | Conteúdo | Faixa/codificação |
|---|---|---|---|
| 56,58,60 | 3×i16 | Giroscópio gx,gy,gz (contagens originais nos eixos do sensor) | ±500 dps, **17,5 mdps/LSB** |
| 62,64,66 | 3×u16 | Quaternion qx,qy,qz (**IEEE-754 fp16**, saída SFLP original) | host recupera w |
| 68,70,72 | 3×i16 | Aceleração ax,ay,az | ±4g, 0,122 mg/LSB |
| 74 | 1 | Byte inferior de `sample_count` | — |
| 75 | 1 | Flags de estado: bit0 pronto, bit1 configurado, bit2 erro | — |
| 76 | 1 | WHO_AM_I = 0x70 (112) | — |
| 77 | 1 | Código de erro do IMU (consulte o enum em `imu.h`) | — |
| 78 | 1 | Estado do clock | — |
| 79 | 1 | Watchdog habilitado = 1 | — |
| 80..83 | u32 | `sample_count` (registros SFLP aceitos, não quantidade de leituras do host) | — |
| 84 | 1 | **`user_marker`, único byte de RAM que pode ser lido e escrito livremente** (a placa não tem LED) | — |
| 240 | 1 | Escrever 0xA5 → solicita reinicialização do IMU; outras operações são recusadas | — |

**Por que o bloco rápido começa em 56:** os servos Feetech disponibilizam nesse mesmo endereço posição/velocidade/carga/tensão/temperatura/estado de movimento (posição i16, velocidade i16 com bit de direção, carga i16, tensão em 62 com unidades de 0,1 V, temperatura em 63 e `moving` em 66). Assim, **uma chamada `SYNC READ 56/12`** lê tanto o giroscópio + quaternion do IMU como o estado de cada servo. O ID distingue os tipos de dispositivo (200 é o IMU; os demais são decodificados como servos). O conteúdo do bloco do IMU mantém o antigo bloco DXL2@124 do microduck (gyro + SFLP xyz), sem alterar o contrato de dados do host.

### 5.3 Bloco de diagnóstico 90..185 (24×u32, 96 bytes, revisão 1)

Durante a validação com `imu_probe`, são lidos os endereços 90/96. Em um sistema saudável, os contadores importantes devem ficar em 0 ou aumentar monotonicamente para refletir eventos reais:

| Deslocamento | Contador | Deslocamento | Contador |
|---|---|---|---|
| 90 | `gyro_count` | 138 | `malformed_packets` |
| 94 | `accel_count` | 142 | `rx_timeouts` |
| 98 | `uptime_ms` | 146 | `rx_packets` (quadros válidos) |
| 102 | idade dos dados do gyro (ms) | 150 | `tx_packets` |
| 106 | idade do quaternion (ms) | 154 | `cancelled_replies` (vezes em que cedeu) |
| 110 | `spi_errors` | 158 | `reset_flags` |
| 114 | `fifo_overflows` | 162 | `clock_hz` (64000000) |
| 118 | `invalid_quaternions` | 166 | `tx_timeouts` |
| 122 | `recovery_count` (reinicializações do IMU) | 170 | `log_dropped` (linhas de log descartadas) |
| 126 | `rx_overflows` (overflow do buffer circular) | 174 | versão da tabela de diagnóstico = 1 |
| 130 | `uart_errors` | 178 | `tx_busy_drops` (transmissões abandonadas porque o barramento estava ocupado) |
| 134 | `checksum_errors` | 182 | reservado (0) |

Cada chamada de `control_table_read` constrói na pilha uma tabela de 256 bytes zerada, obtém um snapshot do IMU e empacota o conteúdo de uma vez. Assim, os dados de uma leitura não ficam inconsistentes (aquisição e callback ocorrem no mesmo loop principal, sem concorrência).

## 6. Fluxo de dados do IMU (`imu.c`)

1. **SPI1, modo 3, 2 MHz** (PCLK/32). Configuração do LSM6DSV16X: ODR do giroscópio/acelerômetro de 120 Hz, giroscópio em ±500 dps, acelerômetro em ±4g, FIFO e saída de postura SFLP (Sensor Fusion Low Power) habilitados.
2. **Amostragem a 120 Hz, consumo a 50 Hz:** há duas atualizações do sensor em cada período do host (20 ms). `imu_poll` esvazia o FIFO uma vez (limite de 16 quadros) e seleciona o registro válido mais recente, o que reduz naturalmente os efeitos de jitter.
3. **Codificação do quaternion:** usa diretamente qx/qy/qz em ponto flutuante de meia precisão IEEE-754 (fp16) fornecidos pelo SFLP. O host recupera `qw` não negativo com `sqrt(max(0, 1 - qx² - qy² - qz²))`. O firmware transmite apenas três componentes para economizar banda; a convenção de sinais pertence ao duck-control upstream.
4. **Semântica de prontidão/falha:**
   - Quando não está pronto, todos os bytes do gyro e do quaternion são **zero** (o upstream continua usando a marcação `not-ready`); acelerômetro e contador continuam disponíveis para diagnóstico.
   - Dados de gyro/quaternion com mais de 100 ms são considerados obsoletos. FIFO, SPI, WHO_AM_I, configuração e validade do quaternion têm códigos de erro independentes (`imu_error_t`).
5. **Recuperação automática:** após uma falha, aguarda 1000 ms antes de repetir a sequência de reset → WHO_AM_I → configuração; o timeout de inicialização é 1500 ms. A recuperação não zera os contadores de ciclo de vida; `recovery_count` registra a quantidade. O host também pode solicitar reinicialização escrevendo 240=0xA5 ou enviar `r` pela porta de log.
6. O loop principal só executa `imu_poll` quando não há comando em recepção nem resposta pendente; o tráfego do protocolo tem prioridade absoluta.

## 7. Loop principal e detalhes do projeto

```c
board_init(); proto_init(..., control_table_read/write, send_packet); imu_init();
for (;;) {
    if (board_bus_take_fault()) proto_reset_receiver();      // reinicia a máquina de quadros após erro UART
    while (board_bus_pop(&byte, &ts)) proto_feed(..., ts);   // esvazia RX primeiro (usa timestamp de entrada)
    proto_poll(now_us);                                      // transmite quando vence o prazo e o barramento está livre
    if (rx_length==0 && pending==0) {                        // sensores/logs somente quando o protocolo está ocioso
        imu_poll();
        processar comandos da porta de log(s/l/r/?); imprimir estado a cada segundo;
    }
    board_watchdog_feed();                                   // IWDG
}
```

- Os logs usam USART1 independente (115200), com buffer circular de transmissão de 512 B; congestionamento só incrementa `log_dropped` e nunca bloqueia o protocolo. O CDC DAP-Link precisa de DTR/RTS em nível alto para produzir saída.
- IWDG fica sempre habilitado (`BOARD_ENABLE_WATCHDOG=1`); o clock HSI16 → PLL 64 MHz não depende de cristal externo instalado.
- Todas as opções de compilação da placa estão centralizadas em `board_config.h` (baud rate, pino RX_EN, velocidade SPI, seleção de interface de log etc.).
- Compilação: `Tools/build.ps1` chama a linha de comando ArmClang; os artefatos e `build.json` ficam em `Build/`; o script do linker é `MDK-ARM/imu_to_dxl.sct`. O Keil mantém apenas o projeto DAP (`imu_to_dxl_dap.uvprojx`).

## 8. Como as ferramentas do host reutilizam o mesmo contrato

As ferramentas Python em `Tools/` são implementações de referência do protocolo e podem ser usadas como referência para desenvolver um host próprio:

- `imu_monitor.py` expõe as primitivas `ft_frame() / checksum() / build_sync_read() / parse_reply()`; analisa o trecho `body = buf[2 : 4+len]` e avança em passos de 4+len, em correspondência estrita com a máquina de quadros do firmware.
- `bus_monitor.py` envia um SYNC READ em broadcast de 56/12, lista `[servos..., 200]` e período de 20 ms; transmite todas as posições-alvo de uma vez com SYNC WRITE `0x83` (addr 42, 2B). Para servos que não respondem a SYNC WRITE, recua automaticamente para gravações individuais. Antes de ler os quadros de cada rodada, limpa os buffers do analisador e da entrada serial, para que respostas atrasadas não contaminem a rodada seguinte.
- Decodificação de dados no host: gyro×0,0175 resulta em dps; converte fp16 → float32 e recupera qw; usa `ready`, `whoami`, idade e contadores de diagnóstico na verificação de integridade.

Ao portar para RK3566 ou outro controlador, é obrigatório manter estas duas regras: **(1) colocar o ID 200 depois dos servos na lista SYNC READ; (2) giroscópio a 17,5 mdps/LSB, quaternion fp16 e recuperação de qw pelo host.**
