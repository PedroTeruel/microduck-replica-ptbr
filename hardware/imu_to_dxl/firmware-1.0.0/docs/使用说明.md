# Manual de uso

Manual de operação no computador de placa única para a placa IMU do Microduck (STM32G031F8P6 + LSM6DSV16X) no barramento Feetech FT-SCS.
A placa IMU usa **ID=200, 1 Mbps**, compartilha a linha com os servos Feetech SCS/STS e pode ser lida junto com eles em um único `SYNC READ`.

---

## 1. Componentes do sistema e fiação

### 1.1 Topologia do barramento

```
   Adaptador USB meia-duplex (COM6)
        │ DATA de linha única + VDD_BUS + GND
        ├── J1/J2 ou J4/J5 ── placa IMU (ID=200)
        ├── servo Feetech (ID=2)
        └── servo Feetech (ID=3) ...
```

- O barramento é **de linha única e meia-duplex**. Todos os dispositivos (placa IMU e servos) compartilham a linha DATA, a 1 Mbps, 8N1.
- A linha `VDD_BUS` alimenta os servos (medição neste equipamento: 8,0 V). Alimente a placa IMU conforme o método de alimentação previsto no hardware.
- **Somente um computador pode enviar comandos ao barramento por vez.** Antes de executar as ferramentas, feche o Feetech FD.exe e qualquer outro software conectado ao barramento.

### 1.1.1 Interfaces J1/J2/J4/J5

| Interface | Pinos |
|---|---|
| J1/J2 | 1=GND, 2=VDD_BUS, 3=DATA |
| J4/J5 | 1=DATA, 2=VDD_BUS, 3=GND |

Use um **adaptador USB para barramento de linha única e meia-duplex**. Um conversor USB-TTL serial comum não consegue controlar diretamente esse barramento.

### 1.2 Porta J3 para depuração e registros (DAP-Link ou USB-TTL)

| Pino J3 | Sinal | Conexão |
|---|---|---|
| 1 | GND | Terra comum |
| 2 | SWDCLK | SWCLK do depurador (somente para gravação) |
| 3 | SWDIO | SWDIO do depurador (somente para gravação) |
| 4 | UART_RX | TX do USB-TTL, 3,3 V (registros a 115200) |
| 5 | UART_TX | RX do USB-TTL, 3,3 V (registros a 115200) |
| 6 | 3.3V | Referência de tensão do depurador; **não conecte a 5 V** |

- A porta serial de registros usa 115200, 8N1. Na inicialização, deve aparecer:
  `imu_to_dxl 1.0.0 | STM32G031F8 | FT-SCS ID=200 1000000 8N1`
- Depois, o firmware imprime uma linha de estado por segundo, por exemplo: `ready=1 id=0x70 ... gyro=... q16=... ck=0`.
- **A porta serial CDC do DAP-Link precisa ter DTR e RTS ativados para receber dados.** No assistente serial, marque essas duas opções de controle de hardware.
- A porta de registros J3 **não responde** a comandos do protocolo do barramento. Para operações com o protocolo, use o adaptador do barramento em COM6.

### 1.3 Portas no computador (Windows)

| Porta | Uso | Parâmetros |
|---|---|---|
| COM6 | Adaptador do barramento meia-duplex (operações do protocolo) | 1000000, 8N1 |
| COM5 | Porta de registros CDC do DAP-Link | 115200, 8N1, requer DTR/RTS |

Confirme os números de porta que o Gerenciador de Dispositivos atribuiu. Informe-os às ferramentas com `--port`.

## 2. Ambiente de software

### 2.1 Ferramentas Python no computador

Requer Python 3.8 ou superior (testado neste computador com Python 3.8.10 de 32 bits) e pyserial. A opção `--plot` também requer matplotlib.

```powershell
python -m pip install -r Tools\requirements.txt
```

Qualquer versão a partir do Python 3.8 serve; confira com `python --version`. Não use o `python.exe` fictício da Microsoft Store.

### 2.2 Construção do firmware (somente ao modificá-lo)

- Keil MDK (neste computador, em `C:\Keil_v5`, com Arm Compiler 6) ou o script de construção.
- Para os testes C no computador, use gcc (por exemplo, `mingw64\bin\gcc.exe` do WinLibs) e adicione a pasta ao `PATH`.

## 3. Construir e gravar o firmware

### 3.1 Construção

No VS Code, pressione **Ctrl+Shift+B** ou execute:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\Tools\build.ps1 `
  -ToolchainRoot 'C:\Keil_v5\ARM\ARMCLANG'
```

Os arquivos gerados ficam em `Build/`: `imu_to_dxl.hex` (para gravar), `.bin`, `.axf` (para depuração) e `.map`.
O firmware atual usa cerca de 10,9 KB de Flash e 5 KB de RAM.

### 3.2 Gravação (importante: use OpenOCD, não a linha de comando do UV4)

**A gravação pela linha de comando do UV4 pode indicar sucesso falso:** retorna código 0 e não mostra erros, mas o chip não é apagado nem regravado. Isso pode ser percebido porque o tempo de atividade nos registros não reinicia. Use OpenOCD com DAP-Link/CMSIS-DAP:

```powershell
& 'openocd.exe' `   # Substitua pelo caminho do OpenOCD no seu computador
  -f interface/cmsis-dap.cfg `
  -f target/stm32g0x.cfg `
  -c 'adapter speed 4000' `
  -c 'program Build/imu_to_dxl.hex verify reset exit'
```

Observação: o arquivo de configuração correto é **`stm32g0x.cfg`**, não `stm32g0x0.cfg`.
Feche o Keil µVision antes de gravar (ele monopoliza o HID do DAP-Link). Se o contato SWD estiver instável, reconecte os fios Dupont.

### 3.3 Verificações após a gravação

1. Na porta COM5, confirme o banner `FT-SCS ID=200` e o estado `ready=1 ... ck=0`.
2. Faça uma varredura conforme a seção 4.1. Devem aparecer os IDs 2 e 3 (servos) e o ID 200 (placa IMU).

## 4. Ferramentas no computador

As quatro ferramentas ficam em `Tools/`. Todas usam `--port COM6` e 1 Mbps.

### 4.1 `servo_tool.py` — varredura de servos e do barramento

```powershell
# Examina os IDs de 1 a 253 e lista todos os dispositivos que respondem (servos e placa IMU)
python Tools\servo_tool.py scan --port COM6

# Monitora o bloco de estado de um servo (posição, velocidade, carga, tensão e temperatura)
python Tools\servo_tool.py read 2 --port COM6 --watch

# Teste de ida e volta de um servo (ele se moverá! Por padrão, 1024<->3072, três ciclos; o torque desliga ao terminar)
python Tools\servo_tool.py test 2 --port COM6

# Gravação direta em registrador (avançado; o firmware ignora escrita de ID/baud rate na placa IMU)
python Tools\servo_tool.py write 200 84 90 --port COM6
```

Na varredura, a placa IMU aparece como `model=0x4d44 fw=1`; os demais dispositivos são servos.

### 4.2 `imu_probe.py` — teste de leitura da IMU

É a ferramenta de validação mais rigorosa: executa PING e lê a identificação, depois consulta periodicamente o bloco de dados de 40 bytes a partir do endereço 56 e o bloco de diagnóstico de 96 bytes a partir do endereço 90. A saída é JSON e pode ser salva em CSV. **Durante todo o teste, ela só envia comandos de leitura e não aciona nenhum servo.**

```powershell
# Coleta por 30 segundos a 50 Hz e salva em CSV
python Tools\imu_probe.py --port COM6 --seconds 30 --csv Build\imu.csv

# Também usa o caminho de SYNC READ de ID único para ler o bloco rápido (verifica 0x82)
python Tools\imu_probe.py --port COM6 --seconds 30 --sync

# Define a taxa de amostragem (1 a 100 Hz)
python Tools\imu_probe.py --port COM6 --seconds 10 --hz 100
```

O código de saída 0 indica que não houve erros de comunicação e que todas as amostras tinham `ready=1`. Um código diferente de zero exige verificar a fiação, a alimentação e a taxa de transmissão.
Os campos incluem `gyro_*_dps`, `q_x/q_y/q_z/q_w`, `ready`, `who_am_i` (=112=`0x70`), `sample_count` e os 23 contadores de diagnóstico.

### 4.3 `imu_monitor.py` — monitoramento da IMU em tempo real

Na frequência definida (50 Hz por padrão), envia um `SYNC READ` de difusão somente ao ID 200 para ler o bloco rápido de 12 bytes no endereço 56. O terminal atualiza em tempo real os dados do giroscópio e o quatérnio. Opcionalmente, é possível abrir gráficos matplotlib ou salvar os dados em CSV.

```powershell
python Tools\imu_monitor.py --port COM6                 # 50 Hz por padrão, atualiza o terminal
python Tools\imu_monitor.py --port COM6 --seconds 10    # encerra após 10 segundos
python Tools\imu_monitor.py --port COM6 --plot          # abre gráficos em tempo real
python Tools\imu_monitor.py --port COM6 --csv imu.csv   # salva amostras válidas
python Tools\imu_monitor.py --port COM6 --rate 100      # altera a taxa de amostragem
```

Ao terminar, mostra os contadores `ok/ck_err/timeout/hw_err`. Para uma execução saudável, `ck=0` e `timeout=0`.

### 4.4 `bus_monitor.py` — monitoramento conjunto da IMU e de vários servos (ferramenta principal)

**Uma única difusão `SYNC READ` (endereço 56, 12 bytes) lê a IMU e todos os servos ao mesmo tempo.** A lista de IDs é ordenada automaticamente como `[IDs-dos-servos..., 200]`; a IMU deve ficar por último, conforme a seção 6. Por padrão, a ferramenta também movimenta os servos suavemente em um movimento de demonstração e desliga ao terminar o torque que ela própria ativou.

```powershell
# Varredura do barramento, painel e movimento de demonstração (1536<->2560, ciclo de 3 s por padrão)
python Tools\bus_monitor.py --port COM6

# Somente monitora, sem movimentar os servos (modo seguro recomendado no primeiro uso)
python Tools\bus_monitor.py --port COM6 --no-demo

# Gráficos em tempo real (giroscópio / quatérnio da IMU)
python Tools\bus_monitor.py --port COM6 --plot

# Define a duração da execução
python Tools\bus_monitor.py --port COM6 --seconds 20

# Consulta apenas os servos selecionados; --srv-id 0 indica que só há a IMU no barramento
python Tools\bus_monitor.py --port COM6 --srv-id 2,3 --no-demo
python Tools\bus_monitor.py --port COM6 --srv-id 0

# Altera a amplitude, a velocidade e o período do movimento de demonstração
python Tools\bus_monitor.py --port COM6 --demo-lo 1024 --demo-hi 3072 `
  --demo-speed 300 --demo-period 2
```

Cada linha do terminal mostra:

- **IMU:** três eixos do giroscópio (dps), quatérnio x/y/z/w e contadores de sucesso/erro.
- **Servo:** posição bruta (0–4095), ângulo (0–360°), velocidade, carga, tensão (0,1 V), temperatura e flag `moving`.

O movimento de demonstração funciona assim:

- Na inicialização, escreve em cada servo: torque ativado (40)=1, aceleração (41)=30, velocidade-alvo (46) e posição-alvo inicial (42).
- Em cada ciclo, envia as posições-alvo de uma vez com **um `SYNC WRITE` de difusão (0x83, endereço 42, 2 bytes)**.
- Se algum servo não responder ao `SYNC WRITE` (não se mover para o novo alvo), a ferramenta volta automaticamente a enviar um `WRITE` individual e informa isso no terminal.
- Ao sair com Ctrl+C ou ao chegar ao tempo definido por `--seconds`, escreve torque=0 em todos os servos que ativou.

> **Segurança:** sem `--no-demo`, os servos se movimentam de verdade. No primeiro teste, deixe-os sem carga e use uma fonte com limite de corrente; confira se não há obstáculos no curso dos braços dos servos.

## 5. Primeira validação da placa

1. Confira a versão do hardware e a alimentação. Primeiro, alimente somente a placa usando uma fonte com limite de corrente; verifique 3,3 V, ausência de curto e de aquecimento.
2. Grave o arquivo hex via SWD com OpenOCD (seção 3.2) e confirme que a verificação passou e a placa reiniciou.
3. Conecte os registros pelo J3 (COM5, 115200, DTR+RTS). Confira o banner, `ready=1` e `WHO_AM_I=0x70`.
   - Comandos do terminal de registros: `s` mostra o estado imediatamente; `l` ativa/desativa os registros periódicos; `r` solicita nova inicialização da IMU; `?` mostra a ajuda.
4. Gire e incline a placa. Confira se os dados de gyro e `q16` mudam com a orientação.
5. Conecte somente a placa IMU ao barramento e execute `imu_probe.py`: o código de saída deve ser 0, sem aumento nos erros `ck/uart/spi/fifo`.
6. Conecte um servo Feetech e execute `servo_tool.py scan` e `bus_monitor.py --no-demo`. Confirme que a IMU e o servo são lidos de forma estável no mesmo quadro; a taxa de sucesso deve se aproximar de 100%.
7. Sem carga, confirme que o servo não encontra obstáculos. Depois, use `bus_monitor.py` (modo de demonstração) para testar o movimento conjunto enquanto a placa está apoiada.

## 6. Regra obrigatória para a ordem dos IDs no `SYNC READ`

**Na lista de IDs do `SYNC READ` enviado pelo computador, o ID 200 (IMU) não pode aparecer primeiro. Ele deve vir depois de todos os servos, como último dispositivo, ou ser lido sozinho em um grupo separado.**

- Testes com firmware de servo Feetech 3.46 a 1 Mbps, em 30 rodadas com várias ordens:
  - `[200,2,3]` (IMU primeiro): apenas 3/30 tiveram sucesso;
  - `[2,200,3]` (IMU no meio): 30/30; `[2,3,200]` (IMU por último): 30/30; `[200]` (somente IMU): 30/30.
- Causa: o firmware Feetech prevê seu intervalo e começa a responder cerca de 180 µs depois do início da resposta do dispositivo anterior. Quando a IMU está primeiro, a resposta do servo pode coincidir com os bytes finais da resposta da IMU, incluindo o checksum.
- As ferramentas deste projeto já respeitam a regra: `bus_monitor.py` sempre usa `[IDs-dos-servos..., 200]`; `imu_monitor.py` consulta somente `[200]`. **Implemente a mesma ordem no computador principal, inclusive na porta do RK3566.**

## 7. Solução de problemas

| Sintoma | O que verificar |
|---|---|
| A varredura não encontra nenhum dispositivo | Confirme que a porta é a do adaptador do barramento (COM6), não a porta de registros; verifique direção meia-duplex, VDD_BUS/GND, 1 Mbps e se outro software está usando o barramento. |
| Só aparece o servo ou só aparece a IMU | Verifique alimentação, conexões, baud rate e se o firmware Feetech foi gravado na placa IMU (o firmware antigo DXL2 não responde a quadros Feetech). |
| A leitura conjunta perde quadros ou acusa erro de checksum | Confira se o ID 200 está no início da lista `SYNC READ`; ele precisa ficar no fim ou penúltimo. Verifique se os fios são longos demais e se é necessário um resistor de terminação. |
| COM5 abre, mas não recebe registros | A porta CDC do DAP-Link precisa de DTR+RTS ativados; confira 115200 e se TX/RX dos pinos J3.4/J3.5 estão cruzados corretamente. |
| A ferramenta informa que não houve resposta | Só pode haver um computador no barramento. Feche FD.exe e outros scripts e desligue e ligue a placa novamente. |
| OpenOCD informa `cannot read IDR` | Feche o Keil µVision, que monopoliza o DAP-Link; reconecte os fios SWD e reduza a velocidade para 100 kHz. |
| O comportamento não mudou depois de gravar pelo UV4 | A linha de comando do UV4 pode indicar sucesso falso. Use OpenOCD (seção 3.2). |
| O servo não se move em modo de demonstração | Veja se o terminal informou que voltou à gravação individual; verifique os registradores de modo, torque e velocidade. Primeiro execute `servo_tool.py test`. |
| O servo continua travado depois de sair | Ao sair normalmente com Ctrl+C, o torque é desligado automaticamente. Se houver uma interrupção de energia inesperada, desligue-o manualmente com `servo_tool.py write <id> 40 0`. |

## 8. Testes automatizados (sem hardware)

```powershell
# Adiciona o diretório do gcc ao PATH (para os testes C)
$env:Path = '<diretorio-WinLibs>\mingw64\bin;' + $env:Path
python Tools\test.ps1
```

Os testes cobrem o protocolo Feetech em C (93 casos: montagem de quadros, checksum, resposta ordenada e recuperação de timeout), a simulação da IMU (16 cenários), o mapeamento de registradores (18 casos) e o teste offline do probe Python (9 casos). Eles não precisam de hardware conectado.
