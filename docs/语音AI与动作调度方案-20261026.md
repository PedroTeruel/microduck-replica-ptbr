# 语音 AI 与动作调度：讨论方案

日期：2026-10-26（东京时间）。来源：用户希望用自然说话与鸭子互动，询问豆包、Jev 是否适合选择动作；同时要求实体手柄仅连接时不要阻止音乐律动。

状态：架构建议与候选服务核对，尚未选择或接入云端服务。本文不是部署或真机验收记录。

10-27补充：用户确认“还没开通，先做好配置入口”。网页模型配置与文字试聊基础已安装到duck-0de6，详情见[入口验证与交付状态](superpowers/verification/2026-10-27-ai-provider-settings.md)。硬件语音、实时语音及AI动作调用仍未接通，下面的整体架构继续作为后续方案。

## 建议

先把现有坐下、站起、头嘴动作、原生叫声、保存的回放和音乐律动接到共同动作入口，再接一种语音理解服务。AI 选择动作或表现风格，本地执行程序检查当前状态、等待完成并处理接管。平衡、步态、关节限位和逐拍律动继续由本地程序负责。

保留 R3 单击开始监听、再次单击关闭，以及不同开关提示音。用户希望以鸭叫回应，因此自由人声合成不是第一阶段必需项。

## 三种可比较的方案

| 方案 | 适用范围 | 需要补齐及限制 |
| --- | --- | --- |
| 现有本地识别与明确口令 | 已支持的坐下、站起等短口令；基础功能可独立于云端保留 | 目前有约束语法，不是完整自然语言识别；不能直接把丢失的信息交给后续模型恢复。 |
| 完整语音识别 + Jev 决策 | 从规定动作中选择意图、识别否定、选择叫声或风格 | 需另有语音识别；要实测中文、背景音乐、否定与不确定输入。复杂先后动作应由明确工作流组合，不能假定一次分类能生成任意可靠计划。 |
| 豆包实时语音 + 工具调用 | 需要上下文的连续自然互动，同时选择已注册动作 | 是首个完整语音服务候选；要验证当前网络下的延迟、音乐干扰、打断、费用及叫声输出策略。接口能力不等于这只鸭子已经验收。 |

建议只接一种理解引擎做首轮对照，不同时叠加豆包、Jev 与第三个模型。接口保留替换能力。若首轮目标是连续自然互动，优先评估豆包；若目标收敛为少量动作意图与鸭叫选择，可评估语音识别 + Jev。

## Jev 的核对结果

用户描述“JEV 啥的”可能对应 TypeSafe 的 Jev，名称仍是推测。官方文档介绍它接收状态与预先定义的问题，返回结构化决策。Choice 可以从选项中选择，并提供概率与置信度；它的定位适合动作路由。结构格式正确不代表意图判断永远正确。

在本方案里，Jev 位于语音识别之后。没有据此认定它能替代整套收音、分句、语音识别、对话与运动执行。

## 本地动作入口与控制权

建议流程：麦克风 → 语音识别/理解 → 受限动作选择 → 本地调度 → 现有运动策略与声音。

- 动作入口只接受已注册动作及有范围的参数。例如“坐下”“站起”“开始/停止律动”“播放某段已保存回放”“播放某种叫声”；不开放任意机器人 RPC、程序执行或关节角度生成。
- 多步骤指令逐步执行，先等坐站回读确认，再进入下一步；超时、中止或状态失效就结束当前流程，不能继续发送旧动作。
- 急停始终优先；明确的手柄操作优先于自主动作。仅蓝牙已连接应与实际输入分开判断。需要统一协调当前 padd 与网页的写入，不能仅删除网页连接保护。
- 音乐律动是持续本地活动；网页负责开关和显示。是否允许离开网页继续，需要与现有录制/回放的失焦停止规则分别设计，不能全局放开。
- 节拍由麦克风在本地持续估计；AI 可较慢地选择轻快、低沉或摇摆表现。提问回应时暂避自己的叫声，防止扬声器反馈被当成新指令。
- 未知或低可信指令不触发动作。网络断开后取消尚未执行的云端动作，保留本地急停与手动控制。

## 当前音乐不晃动的调查边界

这项问题尚未修复或通过真机验收，不能记为接上 AI 就会解决。

现有设备只读记录显示：实体手柄均已断开；音频服务在监听且音乐模式开启，但采样时没有持续稳定的 BPM。ALSA 在 48 kHz 下的 period_size 为 6000 帧，即约 125 ms；当前程序每次读 20 ms 数据，并以读取时刻作为观察时间。状态时间戳表现出约 125 ms 成批到达，需用相同音频在均匀与成批交付下作对照，确认对节拍识别的影响。采样时真实播放内容未同步标注，不能将这个因素直接认定为唯一根因。

另一个已知限制是网页音乐律动沿用动作会话的前台与心跳要求，离开页面可能停止；实体手柄仅连接就被阻挡也是现行规则。上述规则与用户希望的持续听歌、手动随时接管存在差异，需作为明确的控制权设计处理。

数值证据：工作区 `artifacts/audio-interaction-20261025/music-clock.json`、`music-live.json`、`gate-history.json`。这些文件不是原始录音，不作为音乐分类准确率或动作效果验收。

## 后续验收顺序

1. 修稳真实麦克风节拍与时间轴，分别验证头、身体是否跟拍。
2. 验证手柄空闲连接与主动操作的接管规则，避免多个来源争写。
3. 接通共同动作入口，再选择一个语音理解引擎。
4. 用中文变换说法、否定、背景歌曲、网络超时和多步坐站验证；以实际动作回读判定执行结果。
