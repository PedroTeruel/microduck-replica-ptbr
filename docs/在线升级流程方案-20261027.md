# 现有鸭子的在线软件升级流程

日期：2026-10-27（东京时间）。用户根据社区“镜像增加增量更新，避免反复烧录”的讨论，先核对在线升级流程，随后授权实现。本文保留初始方案；同日已完成本地软件、签名包与匹配镜像，实际结果见[交付验证](superpowers/verification/2026-10-27-web-updates.md)和[使用说明](软件更新与语音使用说明-20261027.md)。后续已按用户指示推送源码并公开镜像/软件包，见[发布记录](superpowers/verification/2026-10-27-web-updates-publication.md)；鸭子关闭，未部署或烧卡。下文的“当前/未来”描述为设计时状态，不覆盖交付记录。

## 推荐做法

采用**按组件发布的软件升级包**：网页和语音有更新时只更新相应软件，模型独立更新；系统镜像用于新卡首次安装和系统恢复。第一版的“增量”指不重写整张卡、只下载有变化的组件，组件内部先用完整可复现的版本包，避免二进制差分对每个旧版本都生成补丁。将来下载体积确实成为问题，再增加内容寻址或差分传输；安装与回退流程不依赖差分。

第一批只覆盖Studio网页/后端、与其匹配的小助手及duck-echo语音程序；语音识别模型资源可按哈希复用，不必每次重下。小助手以需要时才重启/替换的关联组件处理。飞特robotd/padd、动作模型、系统底座分别有自己的更新合同，先不混入网页更新。用户界面仍可展示为一个“整套软件版本”，内部维护各组件版本与依赖。

## 用户看到的完整流程

| 步骤 | 页面与实际行为 |
| --- | --- |
| 1. 查看版本 | 设置新增“软件更新”，列出当前整套版本、组件版本、最近更新结果；版本由实际运行字节和安装记录确定，不能只显示现有通用`0.1.0-dev`。 |
| 2. 检查更新 | 鸭子从维护者的发布地址取得受信版本清单，显示新功能/修复、下载大小、支持的硬件与系统、要重启哪些服务和回退范围。没有更新、不能上网、版本不匹配分别说明。 |
| 3. 下载到本机 | 下载至独立临时目录，可重试；按声明大小和磁盘余量设限，校验签名、包hash、解包清单和兼容性。下载失败保留当前软件，不能显示安装成功。 |
| 4. 点“立即更新” | 真正切换前再次检查电量/供电、磁盘、操作占用和最新机器人状态。网页/语音包沿用已验证的“停下站好、策略关闭”前置条件；不能仅凭摇杆归零判定。运行时/模型包需各自确认安装姿态，不能套用“站着重启robotd”。准备不满足时显示具体原因，保持当前版本。 |
| 5. 备份并切换 | 单一更新任务加锁，备份需迁移的数据和上一版，写持久事务记录。由独立更新服务停止必要服务、切换到完整新版本，再启动；正在被更新的网页后端不能兼任唯一执行器。 |
| 6. 验证并恢复页面 | 校验新版本实际文件/运行身份、服务接口、静态资源及关键配置。网页短暂断开时显示“正在更新，等待重新连接”；恢复后按任务ID读取真实结果，不靠旧页面倒计时宣布成功。通过后记录当前版本，保留上一版。 |
| 7. 失败自动回退 | 启动或检查失败时恢复上一版及兼容的数据快照，并验证旧版能运行。断网后可使用本机已有包回退。手动“退回上一版”也走同一条执行路径；不可逆数据迁移的更新必须在发布前说明并提供可验证的恢复方案。 |

日常默认**用户点更新才安装**。检测到新版本不自行重启或切换软件；不照搬上游默认的强制最低版本自动应用策略。第一版无需新增定时任务。

## 第一次接入与之后的更新

当前鸭子的网页尚无更新入口，需要首次通过SSH安装兼容的更新服务、信任公钥和网页入口，并登记现有组件基线；这是一次性引导，不要求重烧卡。首次引导自身也必须备份和验证。以后网页点更新即可。

新做的基线镜像预装相同的升级器和版本清单。新镜像安装与旧卡升级使用同一批签名组件包及安装规则，使“新烧卡”和“旧卡升级”最终到达相同的软件版本。旧镜像先识别机型、运行时、安装路径和实际文件hash，再走支持的迁移入口；未知或被改过的状态明确报告，不盲目覆盖。

在线下载要求**鸭子本身能访问发布地址**。电脑/手机只负责打开网页和触发任务，有手机流量但鸭子不能上网时，鸭子仍无法自行下载。并行保留“从网页上传已下载的更新包”作为离线入口，使用完全相同的签名、兼容检查和安装器；不是浏览器上传任意脚本后执行。

发布地址使用GitHub Releases或能从目标网络访问的HTTPS文件站点。网络条件决定下载体验，但无论从哪里下载都按内置公钥验证签名；不能因为某地址连不上就关闭验证或带用户凭据跳转到陌生地址。

## 更新包和数据边界

发布者构建一次版本包，内容包括：整套及组件版本、源码提交、目标硬件/ARM64/系统与Python要求、组件接口依赖、文件清单与hash、压缩/展开大小、所需服务、数据迁移/回退说明、健康检查和变更说明。以维护者私钥签名，鸭子只装公钥。配置和执行动词由本机更新器白名单控制；网页不能下发任意shell命令或替换更新源。

用户数据与程序版本目录分离，升级不能用发布者机器的配置覆盖用户设备：

- 保留舵机零位、方向、限位、IMU校准/安装方向及现有调参。
- 保留Wi-Fi、手柄配对、设备身份、SSH与网页登录设置。
- 保留导入的模型、当前模型选择/键位、设备档案、已保存动作和语音偏好。
- 保留已保存的AI连接与API Key。含Key的数据备份保持私有权限，不进入发布包、日志或诊断。

程序版本目录采用完整快照及原子指针切换；下载未完成或解包未验证的目录不可运行。切换前后持久化事务步骤并验证，以便更新进程异常退出/设备重启后辨认应继续验证还是回退。断电恢复是验收项目，不能仅凭`os.replace`或“有备份”声称掉电一定可恢复。

## 本地核对结果与复用判断

| 现有资产 | 已核对事实 | 如何使用 |
| --- | --- | --- |
| 原版updaterd源码 | 本地Rust更新器包含清单、签名验证、下载、版本目录/切换、健康检查、回退、UNIX IPC和本地来源；配置有组件安装目录、服务动作和自定义命令健康检查。 | 优先用现有引擎做兼容性验证，再决定适配范围，避免重复实现完整更新事务。 |
| 原版部署配置 | 默认daemon目录为`/opt/robot/daemon`，更新源/签名属于上游，还配置了周期检查及mandatory自动应用。 | 当前飞特运行时和Studio目录不同，不能直接启用原配置。复刻栈需自己的组件配置、受信发布来源和公钥，用户点安装策略。 |
| 当前Studio | 从`/home/radxa/studio-dev`运行，网页无在线更新路由；用户状态默认在`/var/lib/microduck-studio`或源码目录state。 | 先迁移成可回退的程序版本目录，状态保留在版本之外；现有URL/登录维持。 |
| duck-echo | 独立`/opt/duck-echo`运行，安装脚本只重启自身，已有固定运行文件列表及安装回退。 | 独立组件；识别依赖/模型资源单独管理，保留用户默认设置。 |
| 最近单机SSH更新 | 已做冻结提交、变更文件hash、停稳回读、私有备份、失败恢复及部署后HTTP/hash/12个原用户文件/核心进程身份检查。 | 这些是更新器的实际验收基础，不等于已经有公开通用OTA。 |
| 镜像脚本 | 现有构建按payload清单核对文件，并写镜像/Studio来源信息；干净化个人配置。 | 未来改为消费同一套签名组件版本包，不把开发中SD卡复制成公共镜像。 |

现机updaterd在前次盘点中inactive/disabled，本轮没有重新查服务或启用它；源码中存在的功能不能直接当作当前设备已安装的能力。先在假root/临时目录验证现有引擎可管理Studio和duck-echo及其恢复，再编入首个引导包。若设备旧引擎缺少必要接口，明确升级引导组件，不让网页绕过签名或执行任意root脚本。

## 实施顺序与验收

1. 固化当前已部署的Studio991bb50、语音2f24a6a及实际依赖/运行时信息为**待制作的首个基线包**；先核对所有运行字节，不把暂停的AI语音草稿装进去。补统一组件版本登记。此处不是宣布已打包发布。
2. 做同一个安装器的本地包安装、验证、回退和日志，优先验证现有updaterd适配。假root测试覆盖错签名/错硬件/版本跨度、解包越界、空间不足、配置迁移失败、并发安装、服务起不来、执行器崩溃与断电恢复。
3. 加网页登录后的“软件更新”页面和最小受限代理，复用登录/Origin/CSRF；上传/检查/下载、安装、回退、状态各自明确，不把检查更新和安装混成一步。
4. 当前鸭子一次性安装引导包；实物验证失败回退、用户数据保留、网页重连及按实际需要重启服务。专门确认Studio失败时独立更新服务仍可恢复。
5. 同一批包再装进新镜像；验证旧卡升级和新卡首装达到相同程序hash，公共镜像无个人网络/Key/录制数据。
6. 上述通过后再扩大到飞特运行时与模型更新，并单独验证主程序停机姿态、模型执行合同与回退。通用OS/内核/引导的A/B升级不作为这轮日常软件更新的前置条件。
