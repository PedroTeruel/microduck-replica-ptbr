# Fluxo de atualização de software online para os patos já em uso

Data: 27/10/2026 (horário de Tóquio). Após uma discussão na comunidade sobre adicionar atualizações incrementais à imagem e evitar regravações repetidas, o usuário pediu que verificássemos o fluxo de atualização online e depois autorizou a implementação. Este documento preserva a proposta inicial. No mesmo dia, foram concluídos localmente o software, o pacote assinado e a imagem correspondente; os resultados reais estão no [registro de entrega e validação](superpowers/verification/2026-10-27-web-updates.md) e nas [instruções de uso](SoftwareAtualização e 语音Instruções de uso-20261027.md). Depois, conforme solicitado, o código foi enviado e a imagem/pacote de software publicados; consulte o [registro de publicação](superpowers/verification/2026-10-27-web-updates-publication.md). O pato estava desligado; não houve implantação nem gravação de cartão. As referências abaixo a “estado atual/futuro” descrevem o momento em que a proposta foi escrita e não substituem o registro da entrega.

## Abordagem recomendada

Publicar **pacotes de atualização por componente**: quando houver atualização da interface web ou da voz, atualizar somente o software correspondente; os modelos são atualizados separadamente. A imagem do sistema serve para instalar cartões novos pela primeira vez e para recuperar o sistema. Na primeira versão, “incremental” significa não regravar o cartão inteiro e baixar somente os componentes alterados. Dentro de cada componente, usar pacotes completos e reproduzíveis da versão, evitando gerar um patch binário para cada versão antiga. Se o tamanho do download realmente se tornar um problema, acrescentar endereçamento por conteúdo ou transferência diferencial; a instalação e a reversão não devem depender dessas diferenças.

O primeiro grupo inclui somente Studio web/backend, o helper compatível e o programa de voz duck-echo. Os recursos do modelo de reconhecimento de fala podem ser reutilizados por hash, sem baixá-los novamente a cada atualização. Reiniciar ou substituir o helper somente quando necessário para os componentes associados. O runtime Feetech robotd/padd, os modelos de ação e a base do sistema têm contratos de atualização próprios e não devem ser misturados inicialmente à atualização web. A interface pode mostrar uma única “versão completa do software”, mantendo internamente as versões e dependências de cada componente.

## Fluxo completo visível para o usuário

| Etapa | Página e comportamento |
|---|---|
| 1. Consultar versões | Adicionar “Atualização de software” às configurações, mostrando a versão completa atual, as versões dos componentes e o resultado da última atualização. Determinar a versão pelos bytes realmente em execução e pelos registros de instalação; não mostrar apenas o valor genérico atual 0.1.0-dev. |
| 2. Verificar atualização | O pato consulta uma lista confiável de versões no endereço de publicação do mantenedor e mostra novos recursos/correções, tamanho do download, hardware e sistema compatíveis, serviços que precisarão reiniciar e escopo da reversão. Informar separadamente quando não houver atualização, quando não houver acesso à rede ou quando a versão for incompatível. |
| 3. Baixar para o dispositivo | Baixar em um diretório temporário separado, permitindo retomar; limitar pelo tamanho declarado e pelo espaço disponível; verificar assinatura, hash do pacote, lista dos arquivos extraídos e compatibilidade. Se o download falhar, manter o software atual e não mostrar instalação concluída. |
| 4. Escolher “Atualizar agora” | Antes da troca, conferir novamente bateria/alimentação, espaço, operação em andamento e estado mais recente do robô. Para pacotes web/voz, manter os pré-requisitos já validados: parar as atividades, manter o pato apoiado em pé e desligar a política de movimento. Não considerar apenas o joystick centralizado como confirmação. Pacotes de runtime/modelo precisam de confirmação própria da pose de instalação; não reutilizar automaticamente o procedimento “reiniciar robotd em pé”. Se a preparação não estiver pronta, mostrar o motivo e manter a versão atual. |
| 5. Fazer backup e trocar a versão | Bloquear atualizações simultâneas, migrar os dados de backup quando necessário e gravar um registro persistente da transação. Um serviço de atualização independente interrompe os serviços necessários, troca para a nova versão completa e reinicia. O backend web que está sendo atualizado não pode ser o único executor da própria atualização. |
| 6. Validar e restaurar a página | Verificar os arquivos reais da nova versão, a identidade em execução, as interfaces dos serviços, os recursos estáticos e as configurações essenciais. Se a web cair temporariamente, mostrar “Atualizando; aguardando reconexão”. Após a reconexão, consultar o resultado real pelo ID da tarefa; não anunciar sucesso usando a contagem regressiva de uma página antiga. Registrar a nova versão atual e preservar a anterior. |
| 7. Reverter automaticamente em caso de falha | Se a inicialização ou a verificação falhar, restaurar a versão anterior e um snapshot de dados compatível e validar que a versão antiga voltou a executar. Se a rede cair, permitir reversão usando um pacote já armazenado no dispositivo. A ação manual “Voltar à versão anterior” usa o mesmo executor. Migrações de dados irreversíveis precisam ser explicadas antes da publicação e acompanhadas por um método de recuperação validável. |

Por padrão, **a instalação só ocorre quando o usuário escolhe atualizar**. Detectar uma nova versão não deve reiniciar nem trocar software automaticamente; não copiar a política upstream de aplicar automaticamente versões mínimas obrigatórias. A primeira versão não precisa de uma tarefa agendada nova.

## Primeira integração e atualizações seguintes

Os patos atualmente em uso ainda não têm a entrada de atualização web. Na primeira vez, é necessário instalar por SSH um serviço de atualização compatível, a chave pública confiável e a entrada web, além de registrar a versão-base dos componentes existentes. É uma configuração inicial única e não exige regravar o cartão. Essa própria configuração inicial também precisa de backup e validação. Depois, as atualizações podem ser iniciadas pela web.

As novas imagens-base devem incluir o mesmo atualizador e o manifesto de versões. Instalações de imagens novas e atualizações de cartões antigos usam os mesmos pacotes de componentes assinados e as mesmas regras de instalação, para que ambos cheguem à mesma versão de software. Em cartões antigos, primeiro identificar o modelo, o runtime, o caminho de instalação e os hashes reais dos arquivos; depois seguir a entrada de migração compatível. Se o estado for desconhecido ou tiver sido alterado, informar claramente, sem sobrescrever às cegas.

Para baixar online, **o próprio pato precisa conseguir acessar o endereço de publicação**. O computador ou o telefone só abre a interface web e inicia a tarefa; ter dados móveis no telefone não ajuda se o pato não tiver acesso à internet. Também deve existir uma opção offline para enviar pela web um pacote de atualização já baixado. Ela usa exatamente as mesmas verificações de assinatura, compatibilidade e instalação; não executa scripts arbitrários enviados pelo navegador.

O endereço de publicação pode ser GitHub Releases ou um site HTTPS acessível pela rede de destino. A rede afeta a experiência de download, mas todos os pacotes devem ser verificados pela chave pública incorporada, qualquer que seja a origem. Não desative a verificação nem redirecione credenciais do usuário a um endereço desconhecido só porque um endereço de publicação está inacessível.

## Pacote de atualização e limites dos dados

O mantenedor constrói um pacote de versão, uma única vez, com: versão completa e versões dos componentes, commit do código-fonte, hardware/ARM64/sistema e requisitos de Python, dependências das interfaces entre componentes, lista de arquivos e hashes, tamanhos compactado/extraído, serviços necessários, instruções de migração/reversão dos dados, verificações de integridade e descrição das mudanças. Assinar com a chave privada do mantenedor; instalar no pato somente a chave pública. O atualizador local controla, por lista permitida, quais configurações e ações podem ser executadas; a web não pode enviar comandos shell arbitrários nem trocar a origem das atualizações.

Os dados do usuário ficam separados dos diretórios de versão do programa; a atualização não pode sobrescrever as configurações do dispositivo com as configurações da máquina do mantenedor:

- Preservar zeros, direções e limites dos servos, calibração/orientação de montagem da IMU e ajustes atuais.
- Preservar Wi-Fi, pareamento do controle, identidade do dispositivo, SSH e configuração de login web.
- Preservar modelos importados, seleção/associação de botões do modelo atual, perfil do dispositivo, ações salvas e preferências de voz.
- Preservar conexões de IA e chaves de API salvas. Backups que contenham chaves devem manter permissões privadas e não podem entrar em pacotes de publicação, logs ou diagnósticos.

Os diretórios de programa usam snapshots completos e troca atômica de ponteiro; um diretório com download incompleto ou arquivos ainda não verificados não pode ser executado. Persistir e verificar as etapas da transação antes e depois da troca para que, se o processo de atualização falhar ou o dispositivo reiniciar, seja possível determinar se deve continuar a validação ou reverter. Recuperação após perda de energia faz parte dos critérios de aceitação; não se pode garantir recuperação apenas por usar os.replace ou “ter um backup”.

Na última inspeção, o updaterd instalado na máquina estava inactive/disabled; não consultamos novamente o serviço nem o habilitamos nesta rodada. A existência do código-fonte e de suas funções não prova que o atualizador esteja instalado no dispositivo atual. Primeiro, validar o mecanismo existente em um root falso/diretório temporário para instalar e recuperar o Studio e o duck-echo; depois, integrá-lo ao primeiro pacote de inicialização. Se o atualizador antigo não tiver alguma interface necessária, atualizar explicitamente o componente de inicialização, sem permitir que a web ignore a assinatura nem execute scripts arbitrários como root.

## Ordem de implementação e aceitação

1. Congelar os commits implantados Studio 991bb50 e voz 2f24a6a, além das dependências/runtime reais, como **material para o primeiro pacote-base ainda a ser produzido**. Conferir todos os bytes em execução e não incluir o rascunho pausado de voz com IA. Acrescentar um registro unificado de versões dos componentes. Isso não significa que o pacote já foi criado ou publicado.
2. Implementar no mesmo instalador instalação local do pacote, validação, reversão e logs; priorizar validar a adaptação do updaterd existente. No root falso, cobrir assinatura inválida, hardware incompatível, salto de versões, extração fora do diretório, falta de espaço, falha de migração, instalação concorrente, serviço que não inicia, falha do executor e recuperação após queda de energia.
3. Adicionar à web autenticada a página “Atualização de software” e um agente mínimo com permissões limitadas, reutilizando login/Origin/CSRF. Envio, verificação/download, instalação, reversão e estado precisam ficar explícitos; não juntar “verificar atualização” e “instalar” em uma única ação.
4. Criar um pacote de configuração inicial único para os patos atuais. Validar no equipamento a reversão após falha, preservação dos dados, reconexão da web e reinício somente dos serviços realmente necessários. Confirmar especificamente que o serviço de atualização independente consegue recuperar o sistema mesmo se o Studio falhar.
5. Colocar o mesmo pacote na nova imagem e validar que uma atualização de cartão antigo e a instalação inicial de um cartão novo chegam ao mesmo hash de programa. A imagem pública não deve conter rede pessoal, chaves nem dados de gravação.
6. Só depois ampliar o fluxo ao runtime Feetech e à atualização dos modelos; validar separadamente a pose de parada do programa principal, o contrato de execução do modelo e a reversão. Atualização A/B genérica de sistema operacional/kernel/boot não é pré-requisito para a atualização rotineira do software desta rodada.
