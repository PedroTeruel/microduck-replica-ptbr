**Chinês simplificado** · [English](hardware-teardown.en.md)

**方法**：OficialCódigo aberto了 Rust Execução时，而Execução时要驱动真实Hardware，就必须写死设备Caminho、

## 一、整体架构

> 📍 **先说一条最容易搞错的**：**主控板、HAT、摄像头三者都在头里**（MJCF 的 `jaw_soft` 刚体，`robot_walk.xml:235` 与 `:247`），摄像头距主控板中心约 13 mm 且中间没有关节。躯干内腔基本被两颗髋部偏航舵机占满，电池外挂在机身后下方。
> 穿过三自由度脖子的只有两束线：舵机总线和 `+BATT` 供电。
> 详见 [电控Lista de compras · 板子都装在哪](电控Lista de compras.md#先搞清楚板子都装在哪)。

```
                    ┌──────────────────────────────┐
                    │   Radxa Zero 3W (RK3566)     │  65 × 30 mm
                    │   Armbian / 内核 6.1.115      │  Pi Zero 形态
                    └──┬────────┬─────────┬────────┘
          /dev/ttyS2   │        │ 40-pin  │ MIPI CSI
          1 Mbps UART  │        │         │
        ┌──────────────┘        │         └── IMX219 摄像头（转 90°）
        │                       │
        │              ┌────────▼─────────────────┐
        │              │  Pollen RPI Robot HAT    │  65×30mm 自制板(已开源)
        │              │  i2c3 @ 400kHz           │
        │              │   ├ TLV320AIC3104  0x18  │ 音频 codec
        │              │   ├ BMI088   0x19/0x68   │ 焊了但没用
        │              │   └ Stemma J5 → ToF 0x29 │
        │              │  电池经此板供电            │
        │              └──────────────────────────┘
        │
   ═════╪═══════════ Dynamixel 总线 (Protocol V2, 1 Mbps) ═══════════
        │
        ├── 15 × Dynamixel XL330    ID: 左腿20-24 / 颈头嘴30-34 / 右腿10-14
        └── imu_to_dxl v2 板         ID: 200      ← 第二块自制板
              └ LSM6DSV16X
```

**核心设计思想**：**一条 Dynamixel 总线搞定一切**。IMU 不走 I2C，而是做成 Dynamixel
从机挂在舵机总线上，和舵机在**同一次 `sync_read` 事务**里被读出来。
Bateria电压也不用电量计——直接读Servo报告 de 自身供电电压。

## 三、`imu_to_dxl` v2 —— 唯一需要自己画的板

**最巧妙 de 设计，也是最容易自己复刻 de 一块。**

| 项目 | 值 |
|---|---|
| IMU 芯片 | **LSM6DSV16X**（ST 6 轴，带 SFLP Hardware传感器融合块） |
| 接口 | **Dynamixel 总线**（不是 I2C！） |
| 总线 ID | **200** |
| 寄存器地址 | **124** |
| Controle环Leitura | 12 字节 |
| Completo诊断块 | 20 字节（另含original加速度、采样计数、状态标志） |

### 12 字节块布局

| 字节 | Conteúdo |
|---|---|
| `0..6` | gyro x/y/z，`i16` 小端原始计数，量程 **±500 dps**，**17.5 mdps/LSB** |
| `6..12` | SFLP 四元数 x/y/z，**IEEE 半精度 (fp16)**；`w = √(1 − x² − y² − z²)` |

### 为什么这么设计

1. **不占用额外总线** —— 和 15 个舵机在同一次 `sync_read` 里读回，零额外开销
2. **主机不用跑姿态融合** —— LSM6DSV16X  de  SFLP 块在芯片内直接输出游戏旋转四元数，
   还自己估计陀螺零偏
3. **只传 w  de 三个分量** —— 单位四元数省一个字节对，12 字节刚好塞进一次事务

### 📍 这块板装在躯干，不在头里 —— 而且朝向是写死 de 

**这条最容易搞错**，因为主控板e HAT 都在头里，很容易以为三块板都在头里。四条证据：

**① OficialExecução时源码明说了**

`duck-control/src/imu.rs` 开头第一行就是 `//! The imu_to_dxl v2 board (LSM6DSV16X), decoded.`，
而它输出 de 三个量全部标注为躯干坐标系：

```rust
pub struct ImuData {
    /// Angular velocity in the trunk frame, rad/s.
    pub gyro: [f64; 3],
    /// Projected gravity in the trunk frame, unit vector. Upright is `[0, 0, -1]`.
    pub gravity: [f64; 3],
    /// Orientation, trunk→world, scalar-first `[w, x, y, z]`.
    pub quat: [f64; 4],
}
```

**② Instalação朝向是常量，不是随便装**

```rust
/// The board is mounted so that trunk = `[+raw_z, +raw_y, −raw_x]`, a +90° rotation about Y.
pub const DEFAULT_MOUNT: [f64; 4] = [FRAC_1_SQRT_2, 0.0, FRAC_1_SQRT_2, 0.0];
```

即 **躯干 X = 芯片 +Z，躯干 Y = 芯片 +Y，躯干 Z = 芯片 −X**（绕 Y 轴 +90°）。
解码时 `rotate(self.mount, gyro_sensor)` 把传感器读数转到躯干系。

**③ MJCF 里策略用 de 传感器全绑在躯干**

| 站点 | 所属 body 链 | 有无传感器绑定 |
|---|---|---|
| **`imu`** | **`trunk_base`** | ✅ `framequat` / `gyro` / `accelerometer` 全绑它 |
| `head_imu` | `trunk_base > neck > neck_pitch > yaw_roll_motion > jaw_soft` | ❌ 一个都没有 |

`banana_pcb_locker` 在全文**只出现一次**，也在 `trunk_base`（`robot_walk.xml:92`）。

**④ 头里那颗 IMU 是 HAT  de  BMI088，Software不用**

设备树注释原文写 de 是「**dormant** BMI088」「(**unused** but still connected) BMI088」
（`deploy/audio/i2c3-pihat.dts:11,31`），对应上表中没有任何传感器绑定的 `head_imu` 站点。

#### 为什么物理Superior也必须在躯干

策略 de  61 维观测里，来自 IMU  de 只有 **角速度** e **投影重力** 两项，
**它们只取决于 IMU 所固连刚体 de 姿态， e  IMU 装在刚体Superior de 哪个点无关**。

而头挂在 `neck → neck_pitch → yaw_roll_motion` **三个串联关节**之后。
装头里读到 de 是头 de 姿态， e 躯干差着三个关节，而观测里没有脖子角度补偿项 ——
仿真绑躯干、实物装头Superior，sim-to-real 直接失配。

→ **位置在躯干内pode自由选，朝向必须确定并已知。**
朝向若与官方不同，改 `SflpDecoder::new(mount)` 传入自己的四元数即可，该构造函数就是留给这个用的。

#### 锁扣在躯干背面，不在内腔

把 `robot_walk.xml` 里 `trunk_base` 各零件的 `pos`/`quat` 应用到对应 STL 后实测（躯干坐标系，mm）：

| 零件 | X | Y | Z | 尺寸 |
|---|---|---|---|---|
| **`banana_pcb_locker`** | **−32.3 … −28.5** | −27.0 … +27.0 | +31.5 … +38.1 | 4 × 54 × 7 |
| `right_shell` 后缘 | **−27.8** | | | |
| `np_f970` 电池 | −55.3 … −16.7 | ±10.3 | −39.3 … +31.6 | 39 × 21 × 71 |
| `xl330` ×2 髋部偏航 | −8.5 … +20.5 | ±(7.5…27.5) | −13.0 … +21.0 | 29 × 20 × 34 |
| `imu` 站点 | −21.0 | +0.07 | −14.7 | — |

**锁扣 de  X 范围整个落在Direito壳后缘之外**（−32.3 < −27.8），往后 0.7～4.5 mm ——
它是贴在**壳体背面、Bateria顶部** de 一根横压条，**不在躯干内腔**。
在内腔里找不到它是正常 de 。

> ⚠️ 「锁扣压的就是 `imu_to_dxl`」仍是推断 —— MJCF 里没有这块板本身的任何几何。
> 硬约束只有一条：**IMU 必须刚性固连在 `trunk_base` 上**。
>
> ⚠️ 网格文件名叫 `np_f970.stl`，但实测 39 × 21 × 71 mm 是 **NP-F550** 的尺寸，
> 真 F970 厚约 60 mm。见 [BOM  de Bateria型号勘误](../BOM.md)。

### 自己做这块板要什么

- LSM6DSV16X（或引脚兼容 de  ST 6 轴）
- 一颗小 MCU 做 Dynamixel Protocol V2 从机（STM32G0 / CH32V 之类足够）
- 半双工 TTL 收发器（Dynamixel 总线是单线半双工）
- 供电从总线取

**这是整个项目里最值得自己画 de 一块板**，元件少、逻辑清晰、Protocolo公开。

### ⚠️ 打样前必读 de 四条Aviso

**1. 这块板没有充电电路，也没有 USB-C 输入。**

仓库里有张 `pwr_supply_charge.kicad_sch`，很容易让人以为板上带充电。**它是孤儿图纸** ——
`main.kicad_sch` 只实例化了 `audio / dynamixel / power / sensors` 四张子图，没有挂它；
图纸标题栏写的还是别的项目（`Chromapi's Power Supply & Charge`）。

生产 BOM 实测核对：`CN3302`（锂电充电 IC）、`HY2120`（保护）、USB-C 母座、
电源开关、指示 LED、`AO4435`/`FDS6630A` —— **一个都没有**。

板Superior真实存在 de Alimentação器件只有两颗：

| 位号 | 器件 | 作用 |
|---|---|---|
| `U10` | **LM5050-1** | 理想二极管 OR-ing ＋ 关机检测（IO_06）。⚠️ 它在 buck **之后**的 `+5V` 那一路，不是电池输入端的防反接，见下方电源树勘误 |
| `U9` | **AP63205** | 降压变换器 |

> **结论：Bateria必须用外部充电器充。** 插 USB-C 不会给机器人充电。

### HAT 的电源树（原理图第 4/6 页 `dynamixel.kicad_sch` 核对）

```
NP-F550 电池 ──► +BATT ──┬──► J13 / J14  Dynamixel-3（TTL 3P，JST EH 2.5mm）
  2S，6.6–8.2V           │      经 TH1 100R 热敏，原理图旁注「3A max」
                         │
                         ├──► J3 / J11   Dynamixel-4（RS-485 4P，JST EH 2.5mm）
                         │      直接 +BATT，由 U8 SIT3088E 驱动
                         │
                         └──► C19 10µF/63V ──► U9 AP63205 + L4 6.8µH ──► Q2 / U10 LM5050-1 ──► +5V
                                                 2A / Fsw 1.1MHz         理想二极管 ORing         │
                                                                         + 关机检测 (IO_06)       │
                                                                                                  ├─► 树莓派 40 针 J4
                                                                                                  ├─► 音频功放 PAM8406D
                                                                                                  └─► U3 XC6206P182 → +1V8（codec）
```

> `+3V3` 反过来由主控侧经 40 针供给 HAT，不是 HAT 自己产生的。
>
> ⚠️ **勘误（2026-09-04）**：本文此前把 U10 LM5050-1 画成 `+BATT` 的**前级**，**位置错了一级**。
> 按Princípio图 Power 页各符号 de 实际 X 坐标排序：
> `+BATT(153) → C19(219) → U9 AP63205(302) → L4(392) → Q2(558) → U10 LM5050-1(568) → +5V(635)`
> —— **U10 与 Q2 在 buck 之后的 `+5V` 那一路**（配合 IO_06 的「Switch off detection」），
> 不是电池输入端的防反接。**「舵机吃 `+BATT` 电池原压」这个结论不受影响。**

**要点：舵机吃的是 `+BATT`，不是 `+5V`。** 板上只有一颗 buck（U9）和一个电感（L4），
5 V 那一路是给树莓派 de ，2 A 也带不动 15 个 XL330。这就是
[XL330 被超压Execução](执行器选型.md#-电压真相xl330-被超压Execução) de Princípio图级证据。

顺带：HAT 的输入侧按高压设计（`C19 10µF/63V`、`C20 100nF/50V`，注释写着
`Power 24V 5A i.e. 7s/25c, from 21V to 29V`）—— 因为它是 Pollen 给
「small/medium size robots」做 de **通用 HAT**，不是 Microduck 专用。
所以Servo总线电压完全取决于你插什么Bateria；Microduck 插 de 是 2S。

**2. 打开 KiCad 工程é necessário另一个仓库。**

HAT 仓库里**没有** `sym-lib-table`、`fp-lib-table` 或任何 `.pretty` 目录，
但原理图引用了 `Library_Pollen`、`LCSC_parts_lib`、`Lib_Pollen`。这些在
[`pollen-robotics/lib_KiCAD`](https://github.com/pollen-robotics/lib_KiCAD) 里
（`Symbols/Library_Pollen.kicad_sym`、`Footprints/Lib_Pollen.pretty`、`LCSC_parts/`）。

不装它直接打开，会是一片未解析 de 符号。
**只想打样的话不需要** —— 直接用 `production/` 里的 Gerber。

**3. 四层板，118 个贴片位，必须走 SMT Serviço。**

`kicad_pcb` 的层定义是 `F.Cu / In1.Cu / In2.Cu / B.Cu`。BOM 47 行 123 颗元件，
含 **VQFN-32  de  codec** e **LGA-16  de  BMI088** —— 手焊不现实，Inferior单时直接选贴片。

DNP（不贴）共 5 行：`C25`、`R10/R11`、`R16/R17/R41`、`R36/R37`、以及 **`U4`**。

**4. `U4 = CAT24C32` 不贴 → 这不是自识别 HAT。**

EEPROM 位置空着，所以它不符合 `hat-plus-specification` 的自动探测流程，
系统不会自动认出这块板。设备树 overlay 得手动配。

### 板载器件

| 器件 | I2C 地址 | Instruções |
|---|---|---|
| **TLV320AIC3104** | `0x18` | TI 音频 codec，I2S 数据 + I2C 控制 |
| **BMI088** | `0x19` / `0x68` | **真的贴了片但软件不用**（BOM `U11`；注释原文 "dormant"、"unused but still connected"）。外界说 Microduck「有两颗 IMU」指的就是它 |
| **ToF** | `0x29` 或 `0x52` | 不在板上，通过 **Stemma/Qwiic J5** 外接。固件**同时支持 VL53L5CX 和 VL53L8CX**，按 revision ID 自动识别 |

- I2C 总线：40 针的 **pin 3 / pin 5**（`GPIO1_A0` = SDA，`GPIO1_A1` = SCL）
- 总线速率 **400 kHz**（受限于 codec e BMI088；VL53L5CX 本pode跑 1 MHz）
- Superior拉：**单对 10k，R12/R13**
- 音频时钟：MCLK **12 MHz** 固定晶振，I2S sysclk **12.288 MHz**（256 × 48kHz）
- **机器人内部供电经此板**（Bateria → HAT → 主控）

### ⚠️ 一个他们自己踩过 de 坑（注释里写得很清楚）

RK3566 的 `i2c3` 控制器在原厂 DTB 里跑在 **M1 pinmux**（`GPIO3_B5/B6`，靠近 USB-C 口），
服务 **FUSB302 USB-C PD 控制器**。而 HAT 要用的 pin 3/5 正好是 `i2c3` 的 **M0 pinmux**。

他们 de  overlay 把Controle器重新 mux 到 M0，并禁用 fusb302 节点。后果：

- **失去 USB-C PD 协商**
- 但 FUSB302 上电默认在两条 CC 线上呈现 Rd（`SWITCHES0 = PDWN1|PDWN2`），
  所以 USB-C 充电器（无论 PD 还是普通）**仍然给 5V** —— 板子本来就只要 5V
- 机器人内部供电走Bateria经 HAT， e 此无关
- maskrom 刷机是 ROM code，不受影响

> 早期版本用的是 **bit-bang I2C**（`i2c-gpio-pihat`），CPU 占用高。
> 改成Hardware I2C 后才让 **15 Hz  de  ToF 流**变得可负担。
> 两种模式互斥，`install.sh` 通过 `MICRODUCK_I2C_MODE=hw|bitbang` 选择。

### 稳定设备节点

`/dev/i2c-3` 通过 udev 规则软链为 **`/dev/i2c-pihat`**，两种模式下消费者代码不用改。

### 飞特 STS/SCS Protocolo对照

很多人问：**换成飞特Servo之后，「把 IMU 做成总线Superior第 16 个设备」这套还成不成立？**

**成立。** 飞特 STS/SCS 有自己的批量读指令 `SYNC READ`（`0x82`），用法与 Dynamixel 一致。
差别只在**应答怎么回来**。

| | Dynamixel V2（XL330） | 飞特 STS/SCS |
|---|---|---|
| 物理层 | 半双工单线 TTL、3 线、1 Mbps | **完全相同** |
| 接头 | JST EH 2.5 mm | 5264，同为 2.5 mm（⚠️ 间距相同，壳体卡扣细节建议拿实物确认） |
| 包头 | `FF FF FD 00` | `FF FF` |
| 校验 | CRC-16 | `~sum`（取反和） |
| 批量读 | `sync read`（**官方实际用的**）<br>另有 `fast sync read` 0x8A，但**未被使用** | **`sync read` 0x82** |
| 应答方式 | 每设备**一个独立包** | 每设备**一个独立包** |
| 总线转向／周期 | 17 次 ⚠️ | 17 次 ⚠️ |
| ID 范围 | 0–252 | 0–253（寄存器 5） |
| 波特率设定 | 寄存器 `baud_rate = 3` | 寄存器 6，`0 = 1M` |

**证据**：`scservo_sdk/group_sync_read.py` —— `syncReadTx()` 发一条指令包，
`syncReadRx()` 收回一段缓冲，再由 `readRx()` 按 `[0xFF, 0xFF, scs_id]` 逐个匹配包头切分：

```python
result, rxpacket = self.ph.syncReadRx(self.data_length, len(self.data_dict.keys()))
while (rx_index + 6 + data_length) <= rx_length:
    if (headpacket[2] == 0xFF) and (headpacket[1] == 0xFF) and headpacket[0] == scs_id:
        break
```

> ⚠️ **「17 次」是Protocolo推论（1 条指令 ＋ 16 个设备各回一包），不是实测。**
> 换算成毫秒取决于三态缓冲切换速度、包间隙 e 实际Leitura de 寄存器长度 —— 到货用 FE-URT-1 实测。

#### 关键更正：官方**没有**使用 `fast sync read`

Protocol V2 的 `fast sync read`（`0x8A`）确实能把所有应答拼成一个包、把总线转向压到 2 次。
**但 Microduck 的运行时没有用它** —— 全库检索 `fast_sync_read` / `0x8A` **零命中**，
`duck-control/src/bus.rs:236` 调的是普通的 `sync_read_raw_data`：

```rust
.sync_read_raw_data(&self.ids, READ_ADDR, READ_LEN)
.map_err(|e| IoError::Bus(format!("combined imu+motor sync_read: {e}")))?;
```

这也和 `model.rs:84-86` 那句「500 µs **per device** × 16 devices ＝ 8 ms」自洽 ——
**Se应答拼成一个包，per-device  de 转向延迟就不会乘以 16。**

**所以两边 de 应答机制是一样 de **：都是一条指令包出去、每个设备各回一个独立状态包。
飞特并非「没有批量读」，Dynamixel 也并没有在用它那个更快 de 变体。
真正 de 差别只剩两条：**包格式**，eabaixo这条出厂默认值。

#### ⚠️ 一个反直觉 de 发现：出厂延时Superior飞特反而占优

STS 内存表第 `7 (0x07)` 号 **Return Delay Time**：**默认 0**，备注 **"Not functional on STS"**。

而 XL330 出厂是 `250`，即 **500 µs／设备** —— `duck-control/src/model.rs:84-86` 原文：

> `return_delay_time` … the XL330 ships at 250, which is 500 µs of turnaround **per device**.
> Across **16 devices** that is **8 ms per tick — 40% of a 20 ms budget**

Oficial必须把这个寄存器写 0 才能消掉。**飞特天然没有这笔开销**，它多出来 de 转向成本很大程度被这一条抵掉。

#### 飞特侧另一个该调 de 寄存器

STS 内存表第 `8 (0x08)` 号 **Response Level**，默认 **1**（所有命令都应答）。
改成 **0** 之后只有 read  e  ping 回包，普通写指令不再占用总线时间 ——
与官方对 XL330 写 `return_delay_time = 0` 是同一类动作。

> **出厂默认值是给通用场景 de ，高频Controle回路必须自己调。**

## 五之三、为什么必须用 Linux SoC，不能用 STM32 / ESP32

主控要同时干这些事：

| 任务 | 负载 |
|---|---|
| ONNX Runtime 跑策略 | `obs[1,61] → act[1,14]` @ **50 Hz** |
| WebRTC 视频推流 | 720p30 H.264，**Rockchip MPP Hardware编码** |
| RKNN NPU 目标检测 | `duck_detect.rknn`，2 Hz（**热限制**，满速 95°C） |
| GStreamer 管线 + 拥塞控制 | `rtpgccbwe` 占 7.6% 一个核 |
| 蓝牙手柄 + 手机 App + WiFi | BlueZ Protocolo栈 |
| 签名固件更新 / 回滚 | `updaterd` |

**MCU 做不了这些** —— 光是 WebRTC + H.264 硬编 + ONNX 推理就必须 Linux + Hardware编码器 + NPU。

所以选型是：**RK3566 四核 Cortex-A55 + Mali-G52 + NPU，跑 Armbian**。

> 📌 但Atenção：**原型阶段用 de 是树莓派 Zero 2W**。
> `robotd.toml` 注释原文：50 Hz 控制环 *"is inherited from the prototype, where it was
> chosen on a Raspberry Pi Zero 2W. It has never been re-derived on the Radxa."*
> Open Duck Mini v2 至今仍在用树莓派 Zero 2W —— 因为它不做视觉e WebRTC。

### 那 `imu_to_dxl` 板上是什么 MCU？

**仓库里没有** —— 那是板子自己 de Firmware，不在这个Código aberto仓库里。
但从它要干 de 活pode反推需求：

- 做 **Dynamixel Protocol V2 从机**（响应 `sync_read`，ID 200，寄存器 124）
- 读 **LSM6DSV16X**（SPI 或 I2C）
- **1 Mbps UART** + 半双工方向切换
- 把 SFLP 四元数打包成 fp16

**STM32G0 / STM32G4 / CH32V203 / ESP32 都够用。** 这块正好是pode自由选型 de 地方 ——
只要在总线Superior表现得像个 Dynamixel 从机，主控不关心里面是什么芯片。

## 七之二、NPU  e 板载视觉推理

> 本节据上游 `docs/project/npu-bringup.md` 与 `duck-detect/` 整理。
> 这是atualmente唯一一份把「RK3566  de  NPU 到底能干什么」写实 de Material。

### NPU 规格

| 项目 | 值 | Fonte |
|---|---|---|
| 算力 | **0.8 TOPS，INT8，单核** | `npu-bringup.md` 开篇 |
| 设备树节点 | `npu@fde40000` | Armbian 出厂 `status = "disabled"` |
| 运行时 | rknn-toolkit2 运行时 `librknnrt.so` | 驱动 0.9.8 / 运行时 2.3.2（实测） |

### ⚠️ 两条会卡死复刻 de 硬约束

**1. 驱动只存在于厂商内核，mainline 没有。**

> 原文：*"The driver is the gate: it is part of the vendor kernel, mainline has none,
> and nothing in userspace can work around its absence."*

这条比「NPU 默认关闭」严重得多。换成主线内核 de 发行版（大部分 Debian/Ubuntu OficialImagem），
**NPU 直接没有，Usuário态无解**。复刻时系统Imagem不能随便换。

**2. Armbian 在每一块 Radxa Zero 3 Superior都把 NPU 节点关着。**

所以一块「原厂」板子是：Hardware有、内核有、驱动有，**但没有 NPU**。

```bash
# 上游做法：随 robotctl update 的 preinstall hook 自动跑，失败不致命
sudo sh /opt/robot/daemon/current/scripts/setup-npu.sh
# 写 overlay → 必须重启 → 确认：
dmesg | grep rknpu
```

脚本要跑**发布包里那一份**，不能跑 `/usr/local/sbin/robot-setup-npu` ——
overlay 源Arquivoe脚本放在一起，单独那份首次Execução时旁边什么都没有。

### 鸭子检测器

模型训练在另一个仓库 `pollen-robotics/duck_detector`，到这边时已经是量化好的 `.rknn`。

> ⚠️ **该仓库并不公开**（2026-09-04 实测 404）。Oficial文档引用了它，但外部拿不到训练代码，
> 只能拿到成品 `.rknn`。想自己训就得从零搭 YOLO 训练流程。

| 项目 | 值 |
|---|---|
| 网络 | `yolo11n` @ **320×320** |
| 类别 | **1 类**（就是鸭子） |
| 训练集 | **3 个 session 共 150 帧** |
| mAP50 | **0.976**（留出 session Superior） |
| INT8 量化后体积 | **3.9 MB** |
| 量化损失 | 桌面实测 2/2 检出，框重叠 95%（对比 float Modelo） |

> 150 帧就能到 0.976 —— 单类别、固定目标、场景受限，这个量级 de Dados要求
> 对复刻者是好消息。

### 实测性能（Radxa Zero 3，2 Hz 节流，30 帧 × 3 轮）

| 项目 | 实测 | Instruções |
|---|---|---|
| 延迟 p50 / p95 | **25.7 ms / 58.4 ms** | 推理 + 解码，不含 JPEG 解码 |
| 每帧 CPU | 20.7 ms | **Atenção：这不是 NPU  de 开销**，见Inferior |
| SoC 温度 | **63 °C** | 节流跑完时 |

**那个 CPU 数字很容易被误读。** 延迟列算的是 `infer` + `decode`；
CPU 列是整个循环的进程 CPU 除以帧数，因此**还包含 `letterbox_rgb`**——
一次 1280×720 → 320×320  de 重采样，跑在 CPU Superior，且完全不在延迟列里。
剩下的部分是不是 `rknn_run` 忙等（把 NPU 等待算到 CPU 头上），上游自己也还没测清楚。

> 2 Hz Inferior无论如何都只是**单核 de  4%**。但在引用「感知 de 代价」之前，这两块得分开测。

关于 2 Hz 为什么是 2 Hz，见 [§八 值得抄 de 两个工程细节](#值得抄 de 两个工程细节)——
那是**热限制不是偏好**，满速会到 95 °C。

### 三个工程决策值得抄

**1. `dlopen` 而不是链接。** `librknnrt.so` 是厂商 blob，不在任何 Debian 源里；
一旦链接它，CI 里就没法交叉编译。代价是多写一个 `duck-detect/src/rknn.rs`，
好处是 `cargo board --bins` 在笔记本上照样能跑。`robotd` 加载 ONNX Runtime 用的是同一套办法。

**2. 让Execução时做反量化。** 量化Modelo de 输出张量是 int8 + scale + zero point。
`rknn_outputs_get` 可以直接转成 float，上游选择让它转 ——
另一条路是把 scale 带进解码器，**总有一天会悄悄算错一次**。

**3. 排查顺序是「能不能跑 → 还认不认得出 → 花多少钱」。**
`duck-bench` 就是按这个顺序报的。一个能跑但检不出任何东西的模型，
看起来e正常 de 一模一样。

> ⚠️ **量化Modelo de 分数是另一套刻度。** float Modelo de  0.5 不是这个Modelo de  0.5。
> 检不出东西时，先把 `--threshold` 调到 **0.2** 再怀疑转换坏了。

### atualmente还缺什么

**机器人上没有任何东西能拿到一帧图像。** `mediad` 里有一条专为此存在的
raw NV12 tee 分支，但**没有 IPC 暴露它** —— 这也是为什么采集数据集必须先停掉 `mediad`
才能抢到摄像头。

上游给了两条路（不互斥）：一是加 `media.frame` 调用，返回单帧；
二是把检测器搬进 `mediad`，订阅 raw 分支、几 Hz 跑一次、把检测结果发到状态流上。

> 第二条是终局形态：**感知放在传感器旁边，输出特征而不是搬像素**。

### 对复刻者 de 结论

1. **系统Imagem不能随便换** —— 必须是带 Rockchip 厂商内核 de （Armbian 系）
2. 拿到板子第一件事是**开 NPU 节点并重启**，否则一切推理都在 CPU Superior
3. 想自己训Modelo，**150 帧起步**就有可用精度，门槛比想象 em 低
4. 别指望现在就能从机器人Superior取帧做二次开发 —— **这条链路upstream自己还没打通**

### 值得抄 de 两个工程细节

**1. 预测性软着陆（`limp_fall`）**

不是等摔倒了才反应，而是**外推**：投影重力随躯干旋转，其变化率正好是
`-(ω × g)`，用同一个 12 字节 IMU 块里的陀螺数据外推 **300 ms**。
当机器人**已经**倾斜超过约 26°、**且仍在继续倒**、且外推落点越过阈值 →
立刻把增益从 200 降到 **50**，让关节顺着外力走，**软着陆**。
停稳后（用陀螺判断静止，不是定时）再用 600ms 把姿态拉回站姿，
最后才交还给Ficar em pé策略。

> 理由写得很好：Ficar em pé策略「很会Levantar，很不会摔倒」——
> 从静止 de 俯卧/仰卧能干净地起身，但从动态摔倒 em 它会反复尝试并Falha，
> 用走路 de 增益跟地板较劲，电机为每一次尝试买单。

**2. NPU 检测 de  2 Hz 是热限制**

> 注释原文：*"2 is a thermal limit, not a preference"* —— 满速跑会到 **95°C**，
> CPU 降频到 **408 MHz**，那就成了「为了看得清而走不好」 de 机器人。
