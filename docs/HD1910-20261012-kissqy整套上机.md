# 2026-10-12, madrugada · Primeira unidade migrada para a pilha kissqy completa (oficial 0.15.1 + R17 + IMU I²C)

**Em uma frase**: sem regravar o cartão, instalamos remotamente o oficial 0.15.1 e o kissqy R17 no cartão original e adaptamos o `robotd` para ler a IMU por I²C na placa principal. O BNO085 funcionou no robô real; os 15 servos responderam a 50 Hz. O pato executou o HOME oficial e, depois que o modelo assumiu, permaneceu parado por 10 s; a inclinação do corpo caiu de 6,6° para 3,3°. O joystick web não conseguiu iniciar a caminhada: a placa superaqueceu, a CPU caiu para 408 MHz e a interface Python do controle web deixou de responder. O usuário desligou o robô para esfriar; a caminhada ficou para depois de resolver a dissipação térmica.

Este documento explica cada decisão e também serve de referência para assistentes de IA; todos os valores vêm dos logs daquela noite. Para os testes da noite anterior (usando nosso próprio runtime Python com o mesmo modelo), veja [teste no robô de 10-11](HD1910-20261011-kissqy-walk上机实测.md).

---

## 1. Por que migramos para a pilha completa kissqy

Em 10-11, executamos o modelo kissqy com nosso runtime Python. Depois de descartar problemas de ritmo, alimentação, sentido das juntas e parâmetros dos servos, não conseguimos obter uma marcha contínua; todas as diferenças restantes estavam na camada de execução. kissqy já havia demonstrado no grupo que sua pilha completa caminhava bem. Decidimos então: **não instalar nossa própria pilha no robô; usar diretamente o conjunto kissqy e acrescentar somente o que faltava**.

Faltava apenas uma coisa: o programa dele só reconhecia uma pequena IMU no barramento de servos (ID 200), enquanto nossa unidade usava um módulo **BNO085 ligado ao I²C da placa principal** (`/dev/i2c-4`, endereço 0x4B). O código estava pronto na branch local `hd1910-trunk-imu-i2c`, após duas revisões; esta foi a primeira instalação no robô real.

## 2. O que havia no cartão e por que não o regravamos

A princípio, planejávamos gravar um cartão novo. A inspeção remota mostrou que não era necessário:

| Item | Estado encontrado |
|---|---|
| Sistema | Armbian 26.2.1 trixie; cartão de 64 GB usava apenas 2,2 GB; leitura sem erros |
| Runtime oficial | Nenhum instalado (`robotd`, `updaterd` ausentes) |
| Arquivos adicionais | Serviço `microduck-servo-web.service` (iniciado no boot), servo-web, runtime Python e registros em `/home/duck` |
| Inicialização | U-Boot da Radxa + `extlinux.conf`; overlays `uart2-m0` (serial dos servos), `dwc3-peripheral` e `i2c4-m0` (IMU) já presentes |

O overlay `i2c4-m0` havia sido adicionado no fim de setembro para o BNO085; regravar exigiria adicioná-lo novamente. Instalamos sobre o cartão atual. Antes, copiamos `/home/duck`, `/etc` e `/boot/extlinux` para o computador (`home-duck.tar.gz`, 91,6 MB; `etc-boot.tar.gz`, 0,4 MB), para poder restaurá-los sem alterações se houvesse problema.

## 3. Processo de instalação, na ordem

### 3.1 Parar o servo-web

Execute `systemctl disable --now microduck-servo-web`. O serviço ocupava a porta serial dos servos; somente o `robotd` ou o servo-web pode usá-la de cada vez. O arquivo do serviço continua disponível e pode ser iniciado manualmente com `systemctl start`, mas não será iniciado automaticamente no boot.

### 3.2 Instalar o oficial 0.15.1, versão fixada a partir de arquivos locais

- **Por que fixar 0.15.1**: o R17 de kissqy é baseado no oficial `daemon-v0.15.1` (commit `1fa8438`). Na época, a versão oficial já era 0.16.1 (10-07), e o `install.sh` oficial instala somente a versão mais recente.
- **Como fixar**: baixar no computador os seis arquivos do release usando `gh release download daemon-v0.15.1` e transferi-los para a placa. Copiar `install.sh` para `install-local.sh` e alterar apenas dois pontos: fixar a tag `daemon-v0.15.1` e adicionar `--from <diretório-local>` ao comando `updaterd install`. A verificação de assinatura permanece ativa. Depois da instalação, o script também compara se o `updaterd` usado no boot é o mesmo arquivo do release. Alterações:

  ```sh
  # 1. Alterar a linha updaterd install para usar o diretório local
  GITHUB_TOKEN="$TOKEN" "${tmp}/updaterd" install --from "${DUCK_LOCAL_RELEASE}" \
      --config "${CONFIG_DIR}/updater.toml" $force_flag
  # 2. Antes de main "$@" no fim do arquivo: fixar a tag e copiar o updaterd do diretório local
  resolve_bootstrap_asset() {
      RELEASE_TAG="daemon-v0.15.1"
      BOOTSTRAP_URL="${DUCK_LOCAL_RELEASE}/updaterd-bootstrap-aarch64"
  }
  fetch_asset() { cp "$1" "$2"; }
  ```

  Executar: `sudo env DUCK_REF=daemon-v0.15.1 DUCK_LOCAL_RELEASE=<diretório-com-os-arquivos-do-release> sh install-local.sh`.
- **Primeira tentativa falhou**: a preparação tenta baixar do GitHub o ONNX Runtime 1.28.0 (biblioteca Microsoft para inferência do modelo); a conexão direta da placa expirava após 90 s. Configuramos temporariamente um proxy curl para root (`/root/.curlrc`, `proxy = "http://192.168.0.100:7890"`), e o arquivo de 8,1 MB baixou em dois segundos. O proxy foi removido após a instalação.
- **Etapa demorada**: a preparação também instala por apt pacotes do sistema como GStreamer e bibliotecas de câmera; levou 8,5 minutos.
- **Resultado**: `updaterd`, `robotd`, `configd`, `btd`, `padd` e `mediad` estavam todos na versão 0.15.1 e em execução. O `robotd` informou que não encontrou robô no barramento de servos, pois a versão oficial reconhece apenas servos Dynamixel, não Feetech; comportamento esperado.
- **Desativar atualizações automáticas**: em `/etc/robot/updater.toml`, alterar `auto_apply` de `"mandatory"` para `"off"`, para impedir que a versão 0.15.1 atualize sozinha para 0.16 e substitua a base exigida por kissqy.

**Intencionalmente, não executamos dois scripts oficiais:**

- `setup-board.sh`: sua etapa de áudio instala pacotes de kernel vendor do Armbian e aponta `/boot/Image`, `dtb` e `uInitrd` para um kernel novo. Esta placa depende do U-Boot da Radxa para iniciar (veja [registro de problemas · placa principal](../踩坑记录.md#主板--hat--摄像头)); trocar o kernel remotamente poderia impedir a inicialização. O HAT desta unidade tem chip de áudio, mas habilitá-lo exigiria trocar o kernel e compilar o driver. O áudio não é necessário para caminhar, então deixamos desativado. As outras etapas necessárias (overlay serial dos servos e liberação do console serial) já estavam feitas no cartão.
- `migrate-network.sh`: migra a rede de netplan para NetworkManager, necessário apenas para configurar o Wi-Fi por Bluetooth. Fazer a migração remotamente poderia interromper o Wi-Fi e impedir a reconexão; deixamos para depois.

### 3.3 Instalar primeiro o R17 original de kissqy e estabelecer uma referência

Em vez de começar pela versão modificada, instalamos o pacote original `Microduck-Robotd-FT6-R17.tar.gz` (extraído de `Microduck-Firmware-R17-v1.0.146-Public.zip`, todos os arquivos do `SHA256SUMS` conferidos). Assim, seria possível distinguir defeitos originais das nossas alterações. O procedimento é igual a “Manutenção do sistema → Atualização” no painel: extrair e executar `sudo bash Microduck-Robotd-FT6-R17/service.sh upgrade`.

1. **Falha na configuração de áudio**: `alsactl store aic3104` terminou com código 19. O sistema não tinha a placa de som aic3104: o chip de áudio do HAT só é ativado pela etapa de áudio do `setup-board.sh` oficial (kernel vendor + driver), que não executamos; havia apenas o dispositivo HDMI. O mesmo ocorre sem HAT. O script de instalação pressupõe que a placa de som exista. Corrigimos isso na branch (commit `790b45d`): se a placa não existir, ignorar a configuração de áudio e manter o resto; também adicionamos um teste.
2. **Depois da instalação, parou em “Feetech ID 200 sem resposta”**: o programa precisa detectar uma IMU no barramento antes de continuar. A primeira unidade não tem essa placa — era justamente o que precisávamos acrescentar.
3. **O pacote copiou a calibração do protótipo de kissqy para esta unidade**: sem arquivo local de calibração, o instalador gravava os zeros do protótipo de kissqy como os nossos, marcava o estado como “calibrado” e mostrava “pronto para movimento”. Os zeros do protótipo variavam de 1372 a 2176 e os sentidos eram mistos (por exemplo, a cabeça ID 33 tinha zero 1599). Nosso robô havia sido calibrado com servo-web e usa zero 2048 e direção −1 em todos os servos. Aplicar os valores do protótipo forçaria as juntas a ângulos errados.

### 3.4 Instalar nossa versão e configurar a IMU

**Pacote de instalação**: no WSL, extraímos o pacote original, substituímos seis arquivos e recalculamos `SHA256SUMS`; em seguida, criamos `Microduck-Robotd-FT6-R17-imu.tar.gz`, SHA-256 `6c4de6db…`. Foram substituídos `robotd` (`618028ac…`), `robotctl` (`f1bfc8e4…`), `calibration-config.py`, `rebuild-config.py`, `runtime.py` e `voice-setup.py`. Os demais arquivos, modelos e ONNX Runtime permaneceram idênticos byte a byte à versão original.

**Configuração**: acrescentar ao fim de `/etc/robot/feetech-ft5/robotd.toml` e instalar pelo mesmo `service.sh upgrade`:

```toml
[trunk_imu]
source = "bno08x"
i2c_device = "/dev/i2c-4"
i2c_address = 0x4B
```

**Resultado** (modo de depuração, sem habilitar os servos):

- `trunk IMU: BNO08x identified part=10003676 version=(2, 6, 6) build=193`: o BNO085 funcionou no robô real; foi a primeira leitura de um chip real pelo nosso código.
- Os 15 servos responderam; ciclo de controle a 49,99 Hz.
- Cerca de 1,7% das amostras da IMU ficaram “vencidas” (48 de 2.878 quadros passaram de 50 ms). Eram quadros isolados; o ciclo oficial de controle reutiliza a amostra anterior após uma falha de leitura, até três quadros (60 ms), o que, conforme o projeto, não deve afetar a caminhada. A causa não foi investigada; pode estar relacionada à redução de frequência.

**Calibração**: a fórmula kissqy para os ângulos é `ângulo = (leitura − zero) × sentido × 2π/4096`, igual à do servo-web. Definimos zero 2048 e sentido −1 nas 15 juntas com `calibration-config.py copy` (o arquivo do protótipo está guardado em `/home/duck/r17/`). Ao converter os ângulos com a calibração nova, as juntas ficaram simétricas; a maioria estava perto de HOME e ambos os joelhos flexionados cerca de 83°, como esperado do pato sentado sem torque.

### 3.5 Confirmar a orientação de montagem da IMU

O programa kissqy não permite habilitar os servos nem executar HOME antes de confirmar a orientação da IMU. Adotamos essa regra ao acrescentar o suporte I²C. A confirmação tem dois passos: com o corpo vertical, o desvio em relação à vertical deve ser ≤5°; depois, incline o corpo para frente em 15°–30° e confirme que a inclinação apontada está voltada para a frente.

- **Não foi possível fazer segurando o pato mole**: a primeira leitura mostrava desvio de 15,2° em relação à vertical (inclinado cerca de 13° para frente e 8° para a esquerda). Sem torque, as pernas são flexíveis e era difícil manter o corpo reto.
- **Mudamos para ficar em pé primeiro**: clicamos em “pose em pé” no servo-web. Os ângulos eram exatamente os do HOME oficial (quadris ±26,2°, tornozelos ±26°, pescoço e cabeça 20°; conferimos cada valor convertido em leitura do servo). Quando o pato ficou em pé sozinho, lemos a aceleração do BNO085 no servo-web e calculamos a inclinação usando a montagem padrão (`[0.5, 0.5, 0.5, 0.5]`, eixo X do sensor à esquerda, Y para cima e Z para frente):

| Pose | Desvio da vertical | Inclinação para frente | Esquerda/direita | Observações |
|---|---:|---:|---:|---|
| Em pé sozinho em HOME | 4,95° | 4,81° | 1,15° para a direita | 46 amostras, jitter 0,41°, magnitude da aceleração 1,017 g |
| Usuário inclina o pato inteiro para frente | 21,07° | 20,94° | 2,22° para a direita | Variação de 16,2° em relação à pose em pé; direção a 3,9° da frente |

Ambos os valores passaram os critérios kissqy (em pé ≤5°; inclinação para frente ≥12°, direção dentro de 20° da frente), indicando que o módulo estava montado na direção correta. **Como o `robotd` estava parado, gravamos manualmente `[imu_mounts.bno08x] quat = [0.5,0.5,0.5,0.5], verified = true` no arquivo de calibração; não usamos o comando `verify-imu` do `robotd`.** Os critérios eram os mesmos, mas a verificação foi feita fora do programa. A possibilidade de o `verify-imu` confirmar a orientação enquanto o robô está em HOME fica como pendência (§6).

### 3.6 Ativar o modo de movimento, executar HOME e manter a pose

1. `service.sh enable`: muda para o modo de movimento (o script marca a calibração como válida para movimento e inicia o `robotd` nesse modo). O `robotd` iniciou, mas a verificação de prontidão falhou: ele exige que os servos estejam sem torque ao iniciar, mas eles ainda mantinham a pose em pé aplicada pelo servo-web. **A inicialização no modo de movimento não desativa o torque** (a inicialização em modo de depuração desativa).
2. `service.sh init` não conseguiu enviar HOME: esse subcomando exige controle exclusivo do lock do `robotd`; com o `robotd` em execução, informa `another robotd owns this socket`. O painel kissqy envia `robot.init` pelo socket IPC (`/run/robotd.sock`, uma chamada JSON-RPC por linha); usamos a mesma forma.
3. **HOME recusado**: a primeira tentativa expirou ao confirmar o torque; nas quatro seguintes, apareceu `ID 20: temporary P/D readback mismatch; torque-on refused`. Se o programa detectar que os servos **já estão energizados**, presume que ele próprio os ativou e apenas confere se P/D são P5/D20, sem regravá-los. Mas o torque havia sido ativado pelo servo-web e P/D continuavam 32/40, então a verificação falhava.
4. **Desativamos o torque antes de HOME**: com o usuário segurando o pato, enviamos `robot.relax` e, 1,5 s depois, `robot.init`. O log confirmou gravação e leitura de P5/D20, ativou o torque e, após 2 s, chegou à pose HOME (`at the home pose`).
5. **Mantivemos por 10 s**: com o corpo inclinado 6,6°, enviamos `robot.enable on=true`; o modelo assumiu o controle e manteve o robô parado, sem velocidade. A inclinação caiu para 3,2°–3,6° e permaneceu estável; o maior desvio de uma junta em relação a HOME foi 6,2° (o modelo ajustava a pose). Sem erros. Após 10 s, enviamos `on=false` e o robô voltou a HOME.

### 3.7 O painel e o joystick web

- Iniciamos o painel no computador usando o código da branch (`microduck-hd1910/firmware/console/`, `py -3 console.py --dashboard --feetech --open`, navegador em `http://127.0.0.1:8090`) e configuramos SSH para `duck@192.168.0.102`. Esta versão inclui as alterações do painel da IMU e corresponde ao programa na placa. O computador estava com o Clash TUN ativo, mas o SSH do sistema conectou normalmente.
- Depois da conexão, todos os dados estavam corretos: 50,0 Hz estáveis, 15/15 juntas, 15/15 calibradas, modo de movimento, torque ligado, IMU online e montagem confirmada, tensão 7,60 V.
- **O botão Start não respondia**: o caminho do controle web na placa era “painel → webpad (Python, iniciado sob demanda) → controle Xbox virtual → padd → robotd”. O webpad esperava que o `padd` confirmasse a conexão ao controle virtual antes de enviar uma tecla, por até 0,6 s; com a CPU a 408 MHz, só a inicialização do webpad levava 1,7 s. Como a confirmação não chegava, o comando era descartado, o controle virtual era removido e, quando o `padd` tentava abri-lo, o dispositivo já não existia (`Failed to open "/dev/input/event4"`). O `robotd` nunca recebeu o pedido para ativar. A placa principal de kissqy funcionava a 1,8 GHz e não tinha esse atraso.

## 4. Superaquecimento da placa principal (principal problema da noite)

| Momento | Temperatura da CPU | Frequência | Carga em execução |
|---|---:|---:|---|
| Após instalar o oficial + R17 | 89–90 °C | 408 MHz | `gst-plugin-scanner`, do `mediad`, usando um núcleo inteiro (99,5%); `robotd` 35% |
| Dois minutos depois de parar `mediad` e `tofd` | 85 °C | 408 MHz | `robotd` |
| Painel conectado, pato em pé | 86,9 °C | 408 MHz | `robotd`, canal do painel |
| Ao investigar o joystick web | 92,5 °C | 408 MHz | mesmos processos |

- **Por que `mediad` consumia tanta CPU**: não havia câmera conectada; o serviço de câmera `mediad` falhava e reiniciava continuamente, executando o scanner de plugins GStreamer a cada reinício. O serviço de distância `tofd` também reiniciava sem sensor. Desativamos ambos com `systemctl disable --now`; reativar quando instalar a câmera ou o ToF. Outros usuários do grupo também relataram que desligar serviços não usados reduz a temperatura.
- **Mesmo após desligá-los, a placa continuou quente**: a placa principal fica dentro do corpo, sem dissipador nem fluxo de ar. O `robotd` continuou funcionando e a temperatura subiu gradualmente para 92 °C. 408 MHz era a frequência mínima; tudo ficava lento: confirmação de torque expirava, joystick web não respondia e as pausas ocasionais da IMU também poderiam estar relacionadas.
- **Servos**: após cerca de uma hora mantendo força entre a pose em pé e HOME, a temperatura máxima subiu de 40 °C para 63 °C.

O usuário desligou a placa para esfriar. A dissipação precisa ser resolvida antes do próximo teste no robô. Ideia inicial do usuário: abrir alguns furos na cabeça ou no corpo já ajudaria; para uma solução eficaz, o essencial é criar **um caminho de ar**, com entrada e saída — o ventilador não precisa ficar encostado na placa principal. Ao habilitar câmera, ToF e outros recursos, o calor aumentará; planejar a melhoria térmica em conjunto.

## 5. Procedimento para repetir (módulo BNO085; áudio do HAT não habilitado ou HAT ausente)

1. Use um cartão com Armbian inicializável (a placa V1.12 precisa do U-Boot da Radxa; veja [guia sem HAT](不打HAT.md)); confirme `/dev/ttyS2` (servos) e `/dev/i2c-4` (IMU).
2. Pare qualquer processo que esteja usando a porta serial, por exemplo, o servo-web.
3. Instale o oficial `daemon-v0.15.1` a partir de arquivos locais (seção 3.2). Se o ONNX Runtime não baixar, configure temporariamente um proxy curl para root; altere `auto_apply` para `"off"`. Não execute a etapa de áudio do `setup-board.sh` nem o `migrate-network.sh`.
4. Sem câmera ou ToF, execute `systemctl disable --now mediad tofd`.
5. Adicione `[trunk_imu]` a `/etc/robot/feetech-ft5/robotd.toml` e instale o pacote R17 com suporte à IMU I²C (`service.sh upgrade`).
6. **Substitua imediatamente a calibração**: a instalação pode usar os zeros do protótipo kissqy como se fossem desta unidade. Insira seus zeros e sentidos em `hd1910-calibration.toml`, confira os ângulos calculados em relação às juntas reais e só então continue.
7. Coloque o pato em HOME (pode usar a pose em pé do servo-web) e confirme a orientação da IMU: desvio da vertical ≤5° em pé; após inclinar 15°–30° para frente, a variação deve apontar para a frente.
8. Execute `service.sh enable` para mudar ao modo de movimento. Se outro programa ainda estiver aplicando torque, primeiro envie `robot.relax` e depois `robot.init` (HOME). Durante HOME, mantenha o corpo a menos de 10° da vertical.
9. Conecte o painel e aperte Start para ativar a política (modo de manutenção de pose), depois use o joystick para caminhar. **Evite o superaquecimento da placa principal**: em temperatura excessiva, o joystick web pode falhar.

## 6. Pendências e próximos passos

1. **Dissipação**: resolver primeiro (abertura e duto com entrada e saída de ar); depois testar o joystick web e a caminhada. Após reduzir a temperatura, verificar se a CPU permanece acima de 1 GHz.
2. **Joystick web**: repetir após resolver o calor. Se continuar falhando, considerar manter o webpad ativo continuamente ou usar um controle físico (GameSir Nova 2 Lite), que evita esse caminho Python.
3. **1,7% de amostras vencidas da IMU**: investigar a thread de leitura BNO085; pode ser a redução de frequência ou o próprio método de leitura.
4. **Permitir executar `verify-imu` em pé**: o modo de depuração desativa o torque ao iniciar, então não é possível verificar a direção enquanto o pato está em pé. Alternativas: permitir executar a verificação no modo de movimento enquanto HOME está ativo, ou acrescentar no modo de depuração uma opção para manter o torque. Desta vez, gravamos a confirmação manualmente (seção 3.5).
5. **`service.sh init/enable-policy` não funciona com o `robotd` em execução** (diferente do fluxo do painel kissqy); confirmar com kissqy se isso é intencional.
6. **Caminhada**: ainda não testada nesta sessão.
7. Instalar a segunda unidade depois que a primeira estiver funcionando. A publicação da branch no nosso repositório e o envio de um PR a kissqy aguardam uma decisão do usuário.

## 8. Como conectar futuramente um módulo IMU e melhorar a dissipação (ideias ainda não validadas no robô)

### 8.1 Evitar fios diretos para a IMU: há conectores disponíveis no HAT

Atualmente, o BNO085 da primeira unidade usa fios nos pinos 1/6/27/28 do conector de 40 pinos da placa principal (I²C4, `/dev/i2c-4`). O HAT tem conectores de quatro pinos disponíveis (JST-SH de 1,0 mm; 1 GND, 2 3V3, 3 SDA, 4 SCL, igual ao Qwiic). A tabela foi conferida no projeto KiCad oficial (`hardware-official/elec_RPI_Robot_HAT`, `4478fdf`) e na BOM da nossa placa C1:

| Conector | Pinos de 40 vias da placa principal | Uso como I²C |
|---|---|---|
| J5 | 3 / 5 (I2C3) | Sim, I²C por hardware. O uso oficial é ToF (0x29). Na mesma linha está o chip de áudio aic3104 (0x18); na versão C1 — a nossa — também o BMI088 (0x19 / 0x68). Na D1, este foi substituído pelo LSM6DSV16X (0x6A). O BNO085 (0x4A/0x4B) não entra em conflito em nenhuma das versões; um LSM6DSV16X externo deve usar 0x6B na D1. É necessário ativar o overlay oficial `i2c3-pihat`; isso impede a negociação USB-C PD (veja o registro de problemas). Altere `i2c_device` no `robotd` para o caminho `/dev/i2c-N` real. |
| J6 | Por padrão, pinos 7 / 29 via R18/R19 (0 Ω); há pads R16/R17 (0 Ω, sem componentes) para redirecionar aos pinos 27 / 28 | Sim. 27/28 são I²C4, usado atualmente pelo BNO085. **Remova R18 e R19 e instale resistores de 0 Ω em R16 e R17 (ou faça pontes)**. | J7 | 24 / 21 | Pinos SPI com pull-ups de 10 kΩ, não são I²C por hardware. Só é possível usar I²C emulado pelo overlay `i2c-gpio`, com maior carga de CPU e temporização pior que as duas opções anteriores. |
| J8 | 19 / 23 | Igual ao J7. |

O J5 da primeira unidade está livre (não há ToF). Recomendação:

- **Modificar J6** (remover dois resistores 0402 e instalar/pontear outros dois): sem alterar software; a IMU conectada será `/dev/i2c-4` como atualmente e J5 continuará disponível para ToF.
- **Usar J5 sem soldar**: requer alterar o overlay e aceitar que o USB-C deixe de negociar PD; futuramente, o ToF e a IMU poderão compartilhar o mesmo barramento.
