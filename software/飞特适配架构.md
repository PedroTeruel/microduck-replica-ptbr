# Adaptação dos servos Feetech ao runtime oficial · análise de arquitetura e plano

> Estado: **a primeira versão do código foi escrita** em 2026-09-18, na branch `feetech` do fork [`fanhao375/microduck`](https://github.com/fanhao375/microduck), commit `b214486`; ainda não foi testada na placa. Consulte a seção 10 no fim.
> Alvo: runtime oficial da Pollen [`pollen-robotics/microduck`](https://github.com/pollen-robotics/microduck), branch `main` de 2026-09-16 (`768e192`); há uma cópia local em `../microduck/`.
> Servo: Feetech HD-1910-C001, mapa de memória das séries SMS/STS; o original usa Dynamixel XL330-M288-T.

**Resumo:** o runtime oficial encapsula a comunicação com os servos em um trait Rust. Para trocar o protocolo, basta implementar uma nova versão; o ciclo de controle, a política, a segurança, o IPC e o `robotctl` continuam iguais. Além disso, a biblioteca `rustypot` já inclui o protocolo e o mapa de registradores da série STS da Feetech; não é preciso implementar o formato dos pacotes. Os dois desafios reais são as unidades dos ganhos (incompatíveis e gravadas na EEPROM) e a IMU, que não está no barramento. O firmware Feetech tem `REBOOT` (`0x08`); veja §3.4.

---

## 1. Arquitetura existente

### 1.1 Processos e crates

O projeto é um workspace Cargo com 23 crates, cada um correspondente a um serviço ou ferramenta (`docs/design/architecture.md` §1). Apenas três se relacionam aos servos:

| crate | Linhas | Função | Relação com os servos |
|---|---:|---|---|
| `duck-control` | 4.224 | Núcleo de controle: modelo, barramento, observação, política, segurança e simulação | **O protocolo fica aqui**, em `bus.rs` com 708 linhas |
| `robotd` | 12.463 | Daemon: controla a serial, ciclo de controle de 50 Hz e IPC | Abre o barramento, aguarda os servos e inicia a calibração |
| `robotd-params` | 5.435 | Define `/etc/robot/robotd.toml` | `[bus]` tem apenas o campo `port` |
| `robotctl` | 15.560 | Ferramenta de linha de comando | `health` consulta o barramento; `robot reboot-motors` reinicia os servos |

Os demais serviços (`btd` para Bluetooth, `configd` para Wi-Fi, `mediad` para câmera, `padd` para controle, `tof` e `updater`) não acessam os servos.

### 1.2 Uma única fronteira: `RobotIo`

Em `duck-control/src/io.rs`, há **somente esta interface** entre o ciclo de controle e o hardware:

```rust
pub trait RobotIo {
    fn read(&mut self) -> Result<Sensors>;                 // uma transação: 15 juntas + IMU
    fn write(&mut self, targets: &JointTargets) -> Result<()>;   // 15 posições-alvo
    fn set_gain(&mut self, kp: u16) -> Result<()>;         // uma escrita por junta, não a cada ciclo
    fn set_torque(&mut self, on: bool) -> Result<()>;      // idem
    fn reboot(&mut self, id: u8) -> Result<()>;            // REBOOT do Protocol 2, limpa erros de hardware
    fn slow_sensors(&mut self) -> Result<SlowSensors>;     // tensão + temperatura de cada junta, 1 Hz
    fn imu_stale(&self) -> ImuStale { .. }                 // implementação padrão
    fn imu_ready(&self) -> bool { .. }                     // implementação padrão
}
```

As estruturas de dados usam unidades SI e não dependem do protocolo:

```rust
Sensors { positions: [f64;15] /*rad*/, velocities: [f64;15] /*rad/s*/, currents_ma: [f64;15], imu: ImuData }
ImuData { gyro: [f64;3] /*rad/s no referencial do tronco*/, gravity: [f64;3] /*vetor unitário; em pé = [0,0,-1]*/, quat: [f64;4] }
JointTargets { positions: [f64;15] /*rad*/ }
SlowSensors { volts: f64 /*média dos 15 servos*/, temps_c: [f64;15] }
```

Já há três implementações, provando que essa fronteira realmente permite substituir o hardware:

| Implementação | Arquivo | Uso |
|---|---|---|
| `DynamixelIo` | `bus.rs` | Robô real, Linux |
| `FakeIo` | `io.rs` | `robotd --fake`; usado em todos os testes |
| `RemoteIo` | `sim.rs` | `robotd --sim`; corpo simulado no MuJoCo, por TCP + JSON |

A documentação de projeto (`docs/design/simulation.md`) diz: “seis métodos e o único lugar onde um simulador pode existir”. **O backend Feetech será a quarta implementação.**

### 1.3 O que `DynamixelIo` faz a cada ciclo

```text
tick (20 ms)
  read()   uma sync_read: IDs [200, 20..24, 30..34, 10..14], endereço 124, tamanho 12
           ├ slot 0 = placa IMU (ID 200): gyro x/y/z i16 ×3 + quaternion SFLP x/y/z em meia precisão ×3 = 12 bytes
           └ slots 1..15 = servos: present_pwm(2) · present_current(2) · present_velocity(4) · present_position(4)
  decide   observação → política ONNX → alvos
  write()  uma sync_write: goal_position, 15 servos
A cada 1 s
  slow_sensors()  uma sync_read: endereço 144, tamanho 3 → present_input_voltage(2) + present_temperature(1)
```

Conversões de unidades em `bus.rs` (valores copiados do protótipo `microduck_runtime`; os comentários dizem que foram medidos no hardware):

| Grandeza | Registrador XL330 | Conversão |
|---|---|---|
| Posição | 132, i32 | `rad = 2π·raw/4096 − π`, **2048 = 0 rad** |
| Velocidade | 128, i32 | `rad/s = raw × 0.229 × 2π/60` |
| Corrente | 126, i16 | mA, valor absoluto |
| Tensão | 144, u16 | 0,1 V |
| Temperatura | 146, u8 | °C |

### 1.4 Inicialização e encerramento (`robotd/src/main.rs`, `open_bus`)

```text
open_bus(port)
  ├ DynamixelIo::open           serialport 1 Mbps, timeout de 30 ms, rustypot Xl330Controller + Protocol 2
  ├ missing_servos              ping nos 15 IDs
  │    └ falta exatamente 1 → adopt_replacement: encontra ID de fábrica 1 (primeiro a 1 Mbps, depois a 57600),
  │                            grava ID e baud rate, confere registradores e executa REBOOT para limpar erros de hardware
  ├ check_registers             verifica e corrige na EEPROM: return_delay_time=0, baud_rate=3, pwm_slope=255, shutdown=52
  └ falha → tenta de novo a cada segundo; `robotctl health` mostra “no robot on the motor bus after N attempts”

robot.enable / init (só age após comando do usuário; iniciar o processo nunca toca no torque)
  ├ set_torque(true)
  ├ set_gain(kp)                grava P e define I e D como 0 (registradores RAM, voltam ao padrão de fábrica após desligar)
  └ interpolate_to(DEFAULT_POSITION, 2 s)   interpolação linear, bloqueante
```

`JOINT_IDS` e `DEFAULT_POSITION` não dependem do protocolo e serão reutilizados (configuramos os IDs conforme esta tabela). Os quatro valores seguintes são específicos do XL330.

### 1.6 Dependência: `rustypot`

A implementação Dynamixel de `duck-control` usa [`rustypot`](https://github.com/pollen-robotics/rustypot) 1.6.0, biblioteca própria da Pollen. A estrutura é:

```text
rustypot/src
  dynamixel_protocol/   v1.rs (cabeçalho FF FF, checksum de 8 bits)  v2.rs (FF FF FD 00, CRC16)
  servo/
    dynamixel/  xl330.rs  mx.rs ...
    feetech/    sts3215.rs  scs0009.rs  scs0043.rs      ← suporte Feetech já existente
    servo_macro.rs   macro generate_servo!: gera funções read_x / write_x / sync_read_x / sync_write_x para cada registrador
```

**Fatos importantes:**

- `v1.rs` implementa `SyncRead = 0x82` e `SyncWrite = 0x83`, exatamente os códigos usados pela Feetech (o Dynamixel 1.0 não os tem; foram incluídos para a Feetech). Também contém `Reboot = 0x08`, `FactoryReset = 0x06` e `Sts3215Controller::reboot(id)`. Se o servo não responder, o método retorna `Ok(false)`, sem erro.
- `sts3215.rs` usa `generate_servo!(STS3215, v1, ...)` para declarar a tabela completa de memória STS e gerar `Sts3215Controller`. O uso é igual ao `Xl330Controller`: `.with_protocol_v1().with_serial_port(port)`, seguido de métodos como `sync_read_present_position(&ids)`, `sync_write_goal_position(&ids, &rads)` e `sync_read_raw_data(&ids, addr, len)`.
- As duas famílias compartilham a conversão `AnglePosition`: `rad = 2π·raw/4096 − π`. **A Feetech também tem 4096 passos por volta e 2048 como posição central**, então a definição de radianos no ciclo de controle permanece igual.

Em resumo, o formato dos pacotes, o checksum, a leitura/escrita síncronas e os nomes dos registradores **já estão disponíveis**. O SDK oficial Feetech não oferece Rust (apenas C/C++, Python e o aplicativo FD). Existe o [`DoraCN/feetech-servo-sdk`](https://github.com/DoraCN/feetech-servo-sdk) da comunidade, assíncrono com Tokio (MIT, 0.3.0), mas não precisamos dele: o runtime da placa principal já depende de rustypot, e o modelo síncrono é mais adequado ao ciclo de controle de 50 Hz.

## 2. Diferenças entre as duas famílias de servos

A comparação dos mapas de memória usa o SDK oficial FTServo_Linux/src/SMS_STS.h (versão de 2025-09-27), sts3215.rs do rustypot e os documentos Feetech de 2026 em doc.feetech.cn: “SCS Communication Protocol” v1.0 (2026-06-09) e “Magnetic Encoder STS Memory Table Manual” v1.1 (2026-08-27), cujas cópias estão em [docs/飞特资料/](../docs/飞特资料/). Os endereços coincidem nos três materiais; o manual mais novo acrescenta os comandos 0x08/0x09 e esclarece alguns campos.

| Item | XL330 (Protocol 2.0) | Feetech STS/SMS (HD-1910) | Impacto na adaptação |
|---|---|---|---|
| Formato do pacote | `FF FF FD 00 ID LEN INSTR … CRC16` | `FF FF ID LEN INSTR … CHK`, CHK = `~(ID+LEN+INSTR+parâmetros)` | Implementado no rustypot v1 |
| Comandos | PING 1 / READ 2 / WRITE 3 / **REBOOT 8** / SYNC_READ 0x82 / SYNC_WRITE 0x83 | PING 1 / READ 2 / WRITE 3 / REG_WRITE 4 / ACTION 5 / **0x06 restaurar parâmetros** (restaura o backup 0x09, exceto o ID; requer desbloqueio; o manual de 2019 chamava isso de “restauração de fábrica”) / **0x08 reiniciar** (cerca de 800 ms, sem resposta; desligue o torque antes) / **0x09 salvar backup dos parâmetros** / **0x0A reiniciar o estado** (limpa o contador de múltiplas voltas) / **0x0B calibrar posição** (aceita valor; firmware STS ≥ 3.10) / SYNC_READ 0x82 / SYNC_WRITE 0x83 | **Há REBOOT = 0x08**, mesmo código do Dynamixel 2.0; veja §3.4. Não usar 0x06 / 0x09 / 0x0A durante a execução. |
| Baud rate | Registrador 8, `3` = 1 Mbps; fábrica: 57600 | Registrador 6, `0` = 1 Mbps; **já vem de fábrica em 1 Mbps** | Não é preciso trocar a taxa dos servos novos |
| ID de fábrica | 1 | 1 | Igual; a lógica `adopt` pode ser reutilizada |
| Posição | 132 (leitura) / 116 (escrita), i32, 4096 por volta | 56 (leitura) / 42 (escrita), i16, 4096 por volta, **bit 15 é de sinal** (não usado no modo servo, intervalo 0–4095) | Mesma conversão |
| Velocidade | 128, i32, 0,229 rpm/count | 58, u16, bit 15 de sinal; unidade definida pelo BIT2 da fase 18: **0,0146 RPM (= 1 passo/s) ou 0,732 RPM (= 50 passos/s)**. O manual declara precisão de 0,732 RPM nos dois casos. | Converter como `rad/s = raw·2π/4096` (assumindo 1 passo/s); confirmar a unidade na bancada, item 5. |
| Corrente | 126, i16, mA | 69, u16, **6,5 mA/unidade** (manual STS); o manual não descreve o bit de sinal (o SDK usa o bit 15; confirmado no inventário) | A corrente não é usada na observação, apenas registrada |
| Carga | — | 60, u16, 0,1%; bit 10 de sinal | Opcionalmente registrar |
| Tensão / temperatura | 144 (0,1 V) / 146 (°C) | 62 (0,1 V) / 63 (°C) | Vêm na mesma leitura; **não é necessária uma transação lenta separada** |
| Torque | 64 | 40: 0 desativado / 1 ativado / **2 modo amortecimento** (resistência definida pelo limite de torque em 48) / 128 calibração do zero | Similar; decisão sobre amortecimento em §3.3 |
| Ganhos da malha de posição | P 84 / I 82 / D 80, **u16, 0–16383**, RAM | P 21 / D 22 / I 23, **u8, 0–254**, **na região EEPROM (5–39)**; valores P/D de fábrica indicados como “—” no manual (STS3215 costuma usar 32/32), I=0. Com lock=1, gravação não persiste após desligar (texto original do registrador 55 no mapa STS de 2026-08); P descrito como “coeficiente proporcional (1/4)” e D como “coeficiente derivativo (1/8)”. | **Unidades diferentes e registradores EEPROM**; veja §3.3 |
| Modo de operação | 11: 3 = posição | 33: HD-1910 **vem de fábrica em 4 = posição PD pura (Sim2Real)** ([dados antes do treinamento](../docs/HD-1910训练前数据清单.md)). O manual STS genérico lista somente 0 posição / 1 velocidade contínua / 2 PWM / 3 passo, mas a linha de limite integral 25 diz “válido nos modos de posição 0 e 4”, confirmando o modo 4. A especificação HD-1910 descreve 2/3 como corrente constante / PWM; a tabela genérica diz PWM / passo. Usamos a tabela do modelo específico. | **Exigir modo 4, não gravar 0**; calibrar separadamente as escalas de P/D do modo 4. |
| Aceleração / velocidade | profile_velocity 112 / profile_acceleration 108; padrão 0 = sem limite | goal_speed 46 / acc 41; **0 = máximo** | Gravar 0 na inicialização produz comportamento equivalente |
| Atraso de resposta | Registrador 9, fábrica 250 (=500 µs), **precisa ser zerado** | No mapa STS, endereço 7 é **reservado** (o atraso de resposta existe somente em SMS, 2 µs por unidade, mínimo 50) | Não é necessário ajustar |
| Erros de hardware | hardware_error_status 70; `shutdown`=52 é uma máscara | status 65: BIT0 tensão / BIT1 encoder magnético / BIT2 temperatura / BIT3 corrente / BIT5 carga; condição de torque desligado 19 usa os mesmos bits como máscara | Veja §3.4 |
| Proteção contra escrita EEPROM | Não há | **lock 55: escrever 0 desbloqueia, 1 bloqueia** (padrão de fábrica 1). O manual diz: “escrever 1 ativa a trava de gravação; valores escritos em endereços EPROM não são preservados após desligar”. | Envolver `adopt` e as correções de registradores em desbloqueio e bloqueio; **escrita bloqueada equivale a semântica RAM** e será usada em §3.3. |
| Parâmetros de proteção | Máscara shutdown | 19 condição de torque desligado, 28 corrente de proteção, 34 torque de proteção, 35 tempo de proteção, 36 torque de sobrecarga | Já foram habilitados no FD; na inicialização, apenas conferir, sem alterar |
| Deslocamento do zero | homing_offset 20 | offset 31 (bit 11 de sinal) ou comando CAL | Para calibrar o zero na montagem, usar “Calibração do zero” no FD, conforme a etapa 9 do [registro de depuração](../调试记录.md). |
| Convenção de direção | Valores aumentam no sentido anti-horário, vistos pelo lado do horn | **Ainda precisa ser medido**; pode ser o oposto | Se for invertida, inverter o sinal no backend por junta |
| Endianness / versão | — | END 2 = 0 indica little-endian; 0/1 versão do firmware; 3/4 versão do servo | Ler e registrar 0–4 na inicialização; exigir END = 0 |
| IMU | Placa imu_to_dxl no barramento, ID 200, incluída na mesma sync_read | **Não há IMU no barramento** | Veja §3.5 |

## 3. Plano de adaptação

### 3.1 Em geral: adicionar um backend, sem alterar a fronteira

```text
                 ciclo robotd · política · segurança · IPC · robotctl      ← sem alterações
                                    │
                            trait RobotIo (io.rs)
          ┌──────────────┬──────────┴─────────┬──────────────┐
      DynamixelIo     FeetechIo (novo)       FakeIo        RemoteIo
      bus.rs          bus_feetech.rs         io.rs         sim.rs
      rustypot v2     rustypot v1 + STS3215
      XL330 + ID200   HD-1910 ×15 + ImuSource (novo)
```

Arquivos novos ou alterados:

| Arquivo | Conteúdo |
|---|---|
| `duck-control/src/bus_feetech.rs` | `FeetechIo`: implementação de `RobotIo` + `open` / `check_registers` / `missing_servos` / `adopt_replacement` / `present_positions` / `interpolate_to`. Os nomes e assinaturas correspondem aos de `DynamixelIo` para que `open_bus` do `robotd` precise mudar somente o tipo, sem alterar a lógica. |
| `duck-control/src/imu_source.rs` | `trait ImuSource { fn latest(&self) -> Option<ImuData>; fn ready(&self) -> bool }` + implementação `Bno085I2c` (thread própria lê I²C a 100 Hz; o ciclo de controle apenas obtém o quadro mais recente, sem bloquear). |
| `duck-control/src/model.rs` | Adicionar `FEETECH_EXPECTED_REGISTERS` e `FEETECH_FACTORY_ID`; manter `JOINT_IDS` e `DEFAULT_POSITION`. |
| `robotd-params/src/lib.rs` | Em `[bus]`, adicionar `protocol = "dynamixel2" | "feetech-sts"` (padrão dynamixel2, sem alterar o comportamento upstream) e `[bus.feetech]` (`p_scale`, tabela `direction`, `imu = "bus" | "bno085-i2c"`). |
| `robotd/src/main.rs` | Selecionar `DynamixelIo` ou `FeetechIo` em `open_bus` conforme `protocol`; substituir `type BusIo = DynamixelIo` por `enum BusIo { Dynamixel(..), Feetech(..) }` e delegação explícita. **Não usar `Box<dyn RobotIo>`**: `missing_servos`, `adopt_replacement`, `check_registers` e `interpolate_to`, chamados por `open_bus` / `adopt` / `run_init`, não fazem parte do trait; `Safety<T>` também é genérico. |
| `robotctl` | `health` mostra mais uma linha com o nome do protocolo; manter `robot reboot-motors` (a Feetech tem 0x08, §3.4). |

Local da mudança: fazer fork de `pollen-robotics/microduck`, usar a branch `feetech` e manter as alterações nesses pontos. Os padrões da configuração ficam iguais; no futuro, será possível abrir um PR upstream, pois o documento de arquitetura define essa fronteira como o único lugar permitido para trocar a implementação.

### 3.2 Mapeamento a cada ciclo

```text
DynamixelIo                                   FeetechIo
sync_read [200,15 IDs] @124 len 12      →     sync_read [15 IDs] @56 len 15
  bloco IMU + pwm/current/vel/pos                56 pos(2) 58 speed(2) 60 load(2) 62 volt(1) 63 temp(1)
                                                  64 (1) 65 status(1) 66 moving(1) 67-68 (2) 69 current(2)
                                                + imu_source.latest() → Sensors.imu
sync_write goal_position @116 len 4      →     sync_write goal_position @42 len 2
slow_sensors: sync_read @144 len 3       →     sem nova transação; usar 62/63 do último quadro (cache)
```

Uma leitura já traz posição, velocidade, tensão, temperatura, estado e corrente; `slow_sensors` passa a ter custo zero. Tempo estimado no barramento: 15 servos × (6 + 15) bytes ≈ 315 bytes, ou cerca de 3,2 ms a 1 Mbps, mais os intervalos de resposta; escrita: 15 × 3 + 8 ≈ 53 bytes, cerca de 0,5 ms. **Cabe com folga no ciclo de 20 ms** e usa menos dispositivos que a versão XL330 (16).

Conversões:

```rust
positions[j]   = 2π·(raw & 0x7FFF)/4096 − π       // igual a AnglePosition; no modo servo não haverá bit de sinal
velocities[j]  = sign15(raw) · 2π/4096             // passos/s → rad/s
currents_ma[j] = sign15(raw) · CURRENT_MA_PER_UNIT // unidade HD-1910 a confirmar; usar 6,5 do STS3215 inicialmente
volts          = média das leituras de 0,1 V dos 15 servos; ignorar zeros (igual à versão XL330)
temps_c[j]     = raw
```

### 3.3 Ganhos: único item a calibrar, e o ganho Feetech fica na EEPROM

O `kp` de `set_gain(kp: u16)` é o P do XL330. Em `robotd-params`, `gain = 200` é o valor principal; na pose em pé, aplica-se `standing_gain_ratio = 0.8` → 160; ao cair, reduz-se o ganho até `gain_limp = 50` (`limp_fall_pose_gain = 160`). `Safety` memoriza o último valor escrito e não o regrava se não mudou. Porém, cada transição entre caminhar ↔ ficar em pé ↔ cair escreve novamente em todos os servos: 15 × 3 bytes.

O P da Feetech é um byte de 0–254 e tem outro significado físico (quantos PWM para cada unidade de erro), portanto **não pode ser copiado diretamente**. O problema mais sério é que **21/22/23 ficam na região EEPROM**; repetir o padrão XL330 desgastaria a EEPROM a cada mudança de estado.

Plano:

- **Escrever mantendo o bloqueio.** O mapa STS de 2026-08 diz no registrador 55: “escrever 1 ativa o bloqueio de escrita; valores gravados em endereços EPROM não são preservados após desligar”. Ou seja, a escrita é aceita, mas não persiste: exatamente a semântica RAM do XL330. Em `set_gain`, escrever P sem desbloquear evita desgaste e, após reiniciar, o valor volta ao da EEPROM, de acordo com o contrato de `reboot`. O manual não declara explicitamente que o novo valor entra em vigor imediatamente; **confirmar isso na bancada, item 3**.
- **O modo de amortecimento não substitui Limp.** Escrever 2 no torque (40) ativa amortecimento e usa 48 para definir a resistência, parecendo “amolecer”. Mas o `LimpFall::Limp` do upstream significa “ganho baixo, alvo mantido na posição atual, postura ainda sustentada”; o comentário diz explicitamente para não soltar o torque, ou a cabeça bate no chão e a etapa seguinte não consegue interpolar a pose. Portanto, `gain_limp` continua alterando P. Considerar amortecimento somente para “soltar por completo” (por exemplo, `robot disable`). `torque_enable` do rustypot é booleano; para escrever 2, é preciso usar `write_raw_data`. O mapa SMS nem inclui esse valor e é preciso testar no HD-1910.
- Se a hipótese da escrita bloqueada não funcionar, deixar P configurado uma vez no FD durante a montagem e usar `torque_limit` (48), em SRAM, para “amolecer” durante a execução: mapear `set_gain(50)` para um limite proporcional de torque.
- Conversão: `p = clamp((kp × p_scale).round(), 1, 254)`; configurar `p_scale` em `[bus.feetech]`. Calibrar na bancada com a mesma junta e o mesmo degrau, ajustando P Feetech até a resposta ficar próxima à resposta do XL330 com kP=200.
- **Não zerar D.** A versão XL330 grava I e D como 0 porque esses valores já vêm como 0 de fábrica. Na Feetech, D=32 é parte do ajuste do fabricante; zerá-lo com a redução 320:1 pode causar oscilação. Preserve I/D de fábrica e altere somente P.
- A escala de P/D do modo 4 (posição PD pura) pode diferir da escala do modo 0; calibrar no modo realmente usado.

Uma calibração incorreta não impede o movimento, mas **faz a marcha divergir do treinamento**. Por isso, essa verificação está na aceitação de bancada; a política já precisará ser retreinada para HD-1910 (consulte a [lista de dados antes do treinamento](../docs/HD-1910训练前数据清单.md)).

### 3.4 REBOOT: o firmware Feetech mais recente implementa 0x08

No XL330, `RobotIo::reboot(id)` usa REBOOT do Protocol 2 para limpar erros de hardware bloqueados pela máscara `shutdown` (sobrecarga ou superaquecimento). O contrato em `io.rs` é: **ao voltar, o torque do servo está desligado e os registradores RAM voltam aos valores padrão da EEPROM; quem chamou reaplica o ganho**. Quando recebe `reboot-motors`, o `robotd` executa `set_torque(false)` antes e depois define a máquina de estados como `Limp`.

A edição 2026-06 de “SCS Communication Protocol” da Feetech, §4.12, especifica: **comando de reinício 0x08, “reinicia o servo”, sem pacote de resposta, duração aproximada de 800 ms; observação: desligue o torque antes de reiniciar**. É o mesmo código e a mesma função que REBOOT do Dynamixel 2.0. As duas revisões anteriores deste documento afirmavam que a Feetech não tinha REBOOT, com base em um manual de 2019 e no cabeçalho do SDK, ambos desatualizados. Cuidado para não confundir com os outros comandos:

| Comando | Manual 2026-06 | Conclusão |
|---|---|---|
| `0x06` | Restaura parâmetros salvos por 0x09, exceto ID; requer desbloquear a EEPROM | Não usar em execução |
| `0x09` | Salva um backup dos parâmetros atuais | Vale fazer uma vez pelo FD após ajustar o robô |
| `0x0A` | Reinicia o contador de voltas do servo | Não usar em execução |
| `0x0B` | Sem argumento: calibra a posição atual como ponto central; com argumento: calibra para o valor definido; firmware STS ≥ 3.10 | Usar para calibrar o zero na montagem. **No HD-1910, este é o único método que funciona**: escrever 128 no controle de torque não teve efeito nos testes de 2026-09-20, mesmo após desbloquear e desligar o torque; o offset não mudou. O manual diz o mesmo para HLS ≥ 3.43. |

A implementação de `FeetechIo::reboot(id)`: torque 0 → `controller.reboot(id)` (0x08 já implementado no rustypot v1; quando o servo não responde retorna `Ok(false)`, sem erro) → **retorna imediatamente**. Não esperar, pingar ou ler o registrador 65: `Safety::reboot_motors` chama os servos um por um dentro do ciclo de controle; esperar 1 s por unidade bloquearia o ciclo por 15 s. Assim como na versão XL330, os demais bits de 65 só são registrados como erro. A espera e o ping devem ficar em `adopt_replacement` (o `REBOOT_SETTLE` upstream é 500 ms; a Feetech leva cerca de 800 ms; **configurar pelo menos 1 s**) e nos testes de bancada. O manual confirma que o torque volta desligado. A hipótese de que a escrita bloqueada em P retorna ao valor EEPROM após reiniciar ainda precisa ser provada; o manual só especifica o comportamento ao desligar. O teste de bancada, item 3, também vai conferir isso antes de considerar o contrato cumprido. Não é necessário mudar `robotctl robot reboot-motors`. Manter o REBOOT em `adopt_replacement` não serve para limpar um alerta do XL330 (a Feetech não tem esse bit), mas para **confirmar que o novo ID continua definido após a reinicialização**; se o bloqueio de escrita não tiver sido removido, o teste revela o problema.

No item 8 da bancada, bloquear manualmente um servo para provocar sobrecarga (65 BIT5), reiniciar e confirmar que responde ao ping após 1 s, que 65 foi limpo e que o ID foi preservado. Registrar primeiro as versões do firmware HD-1910 (endereços 0/1); o manual não informa se 0x08 existe em todas as versões.

### 3.5 A IMU não está no barramento

Na versão XL330, a placa `imu_to_dxl` está no barramento com ID 200 e os dados voltam na mesma leitura dos servos. No barramento Feetech ela ainda não existe (o firmware da placa não foi escrito). As duas opções para a IMU do tronco continuam em paralelo (veja o [registro de depuração](../调试记录.md)):

| | A · Placa `imu_to_dxl` | B · BNO085 ligado diretamente ao I²C da placa principal |
|---|---|---|
| Como chega a `FeetechIo` | Firmware da placa responde como ID 200 usando o protocolo Feetech; lê um bloco personalizado no endereço 56 e o inclui na mesma `sync_read` (inserir 200 no começo da lista de IDs) | Thread `ImuSource` lê I²C a 100 Hz; `read()` usa o quadro mais recente |
| O que falta para começar | Escrever primeiro o firmware STM32 | Comprar o módulo e confirmar que `i2cdetect` em i2c3 encontra 0x4A |
| Arquivo | Variante em `bus_feetech.rs` | `imu_source.rs` |

A definição de `ImuData` não muda: gyro (rad/s no referencial do tronco), gravity (vetor unitário, em pé `[0,0,-1]`) e quat (tronco → mundo). O BNO085 fornece diretamente o quaternion fundido e o giroscópio. Reimplementar em `Bno085Decoder` a rotação de montagem, o filtro de mediana e o critério `ready()` usados por `SflpDecoder`. **Começar pela opção B**; a opção A aguarda o firmware.

Na parte da IMU em `FeetechIo::read()`, se `imu_source.latest()` não retornar dados, reutilizar o quadro anterior e incrementar `imu_stale`, mantendo a semântica da versão XL330, em que a placa pode devolver o mesmo bloco de dados. `imu_ready()` encaminha diretamente o estado da fonte.

**Manter as duas opções e selecionar uma na configuração** (`[bus.feetech] imu = "bus" | "bno085-i2c"`); os modelos de thread são diferentes:

```text
imu = "bus"          A · placa conectada ao barramento, ID 200
                     Uma thread. Inserir 200 no início da lista de IDs da sync_read;
                     o bloco da IMU volta junto com os 15 servos, igual ao modelo XL330 oficial,
                     mudando apenas o formato do pacote para Feetech.

imu = "bno085-i2c"   B · módulo BNO085 ligado aos pinos 3/5 da placa principal
                     Duas threads:
                       Controle 50 Hz   sync_read dos servos → última amostra da IMU → política → sync_write
                       IMU     100 Hz   leitura I²C (mensagens SH-2) → converter para ImuData → gravar em slot compartilhado (Mutex ou ArcSwap)
                     read() apenas copia o quadro mais recente; não espera pelo I²C.
                     Sem quadro novo, reutiliza o anterior e incrementa imu_stale.
```

Motivos para usar uma thread separada na opção B: a IMU opera a 100 Hz e o ciclo de controle, a 50 Hz; um travamento I²C (fio solto ou perda de alimentação) não pode atrasar o tick dos servos; e as mensagens SH-2 exigem segmentação e controle de sequência, que não devem ocupar os 20 ms do ciclo. Para a camada superior, as duas opções são equivalentes: `Sensors.imu` contém o mesmo `ImuData` e a política não distingue a origem.

**Complementos após a revisão (2026-09-17)**

Opção B (BNO085 ligado diretamente):

- Não reutilizar o decodificador de quaternion SFLP: `SflpDecoder` recebe apenas x/y/z e calcula `w = √(1−|v|²)`, supondo `w ≥ 0`. O BNO085 fornece a componente real, que pode ser negativa; usar diretamente os quatro componentes e converter conforme a convenção da placa (body→world, Z para cima, gravidade = R⁻¹·[0,0,−1]). Recalcular o quaternion de montagem conforme a orientação física do módulo e validar parado em três poses (em pé / inclinado 90° para a frente / deitado de lado).
- `imu_stale` retorna vazio por padrão no trait. A comparação quadro a quadro é feita pelo `StaleImuTracker` de `DynamixelIo`; 25 quadros sem mudança é o limite do aviso. Para B, usar o número de sequência da thread da IMU para detectar “sequência não mudou”; `imu_ready` também deve considerar o campo de precisão informado pelo BNO085.
- Amostragem de 100 Hz da IMU / ciclo de controle de 50 Hz: em cada tick, o controle usa a amostra mais recente; a thread da IMU apenas grava o quadro novo. Não calcular a média de dois quaternions.
- O Game Rotation Vector não tem magnetômetro; o rumo deriva. Como `odometry.update` usa o quaternion, a deriva também afeta a odometria. O SFLP oficial deriva da mesma forma; não é um problema novo.
- I²C: o i2c3 da placa principal, na HAT oficial, também conecta o ToF, o codec de áudio e o BMI088 da cabeça; `tofd` tenta carregar firmware durante a inicialização. Sem HAT, o barramento fica livre, embora `tofd` ainda tente detectá-los. O BNO085 pode manter SCL baixo por muito tempo (clock stretching), algo que o controlador I²C RK3566 não lida muito bem: **depois de conectar, testar 10 minutos de leitura a 100 Hz e registrar jitter e perda de quadros**. Se não funcionar, usar o modo UART-RVC do BNO085 (saída fixa de 100 Hz; ocupa outra serial da placa).

Opção A (placa no barramento):

- O `sync_read` do rustypot recebe e valida os pacotes estritamente na ordem da lista de IDs; se vierem fora de ordem, descarta o tick inteiro. O manual não esclarece se, durante sync_read, os servos Feetech respondem em sequência (aguardando o anterior) ou após um atraso fixo. Na bancada, incluir no início da lista um ID inexistente e observar a resposta dos outros 15; depois medir com analisador lógico o atraso da resposta da placa (em §4.2, **menos de 100 µs**).
- Identificação do protocolo no firmware: travar na primeira solicitação validada; **não tentar desbloquear automaticamente durante a execução**. A proposta antiga de reavaliar após 100 pacotes inválidos poderia deixar a placa muda por 2 s por causa de ruído; após 3 ticks sem leitura, o controlador entra em hold.

### 3.6 Mapeamento da sequência de inicialização

```text
FeetechIo::open(port)        Sts3215Controller::new().with_protocol_v1().with_serial_port(1 Mbps, 30 ms)
missing_servos()             ping nos 15, como na versão XL330
adopt_replacement(id)        ID e baud rate de fábrica 1 / 1 Mbps; sem troca de taxa:
                              desbloquear lock → gravar ID → bloquear → check_registers_of → REBOOT 0x08
                              → esperar pelo menos 1 s → ping no novo ID (confirma que o ID persistiu após reboot)
check_registers()            ler primeiro 0–4 (versão firmware e endianness END) e a fase 18; exigir END 2 = 0.
                              Os bits 2, 3, 0 e 7 da fase definem unidade de velocidade, significado de “velocidade 0” e direção.
                              Exigir: baud 6 = 0 · modo 33 = 4 · nível de resposta 8 = 1 (padrão)
                              · parâmetros de proteção (19/28/34/36) = valores configurados no FD.
                              Se baud estiver incorreto, desbloquear, corrigir e contar como na versão XL330.
                              Para modo, nível de resposta e proteções, apenas avisar, sem corrigir:
                              um modo incorreto pode alterar os 15 servos; pare e peça intervenção.
                              O nível de resposta precisa ser 1: o manual diz que em 0 não há resposta,
                              exceto a comandos de leitura e PING. O write() do rustypot espera status;
                              com nível 0, cada escrita expira em 30 ms.
init                         set_torque(true) → set_gain (§3.3; gravar P mantendo o bloqueio)
                              → interpolate_to conforme implementação existente.
                              Não escrever aceleração 41 / velocidade 46: SRAM inicia em 0 / máximo.
                              “46 = 0 é máximo” depende também do BIT3 da fase; gravar valor pode significar parar.
```

### 3.7 Direção e posição zero

Na versão XL330, não existe uma tabela de direção por junta; 2048 é o zero e os servos foram instalados na mesma orientação do original. Para Feetech:

- Zero: durante a montagem, usar “Calibrar posição central” no FD para definir a pose ereta como 2048 ([etapa 9 do registro de depuração](../调试记录.md)), equivalente a `homing` do XL330.
- Direção: **verificar cada servo na bancada**; comandar +30° e observar para que lado a junta se move. Se o sentido positivo STS diferir do XL330, configurar `[bus.feetech] direction = [±1; 15]` e multiplicar na leitura/escrita do backend. O padrão é tudo +1.

## 4. Firmware da placa pequena (opção A · `imu_to_dxl`)

A placa da opção A ([`hardware/imu_to_dxl/`](../hardware/imu_to_dxl/)) está montada e alimentada, mas **o firmware precisa ser escrito do zero**. Sua função é simples: **se apresentar no barramento como um servo de ID 200 e devolver os dados da IMU quando a placa principal fizer a leitura**. Os requisitos do projeto oficial estão em `duck-control/src/imu.rs` e `bus.rs`:

> 📄 **Especificação do firmware em documento separado:** [`hardware/imu_to_dxl/总线协议.md`](../hardware/imu_to_dxl/总线协议.md)
> — definição do bloco byte a byte; valores de temporização com identificação do que vem do manual ou é inferido; fila para múltiplos dispositivos; sequência de alimentação; quatro critérios de validade da placa principal; duas proibições para o firmware relacionadas à detecção de congelamento; vetores de teste e lista de aceitação.
> Ferramenta correspondente: [`tools/imu200/`](../tools/imu200/), com placa simulada, gerador de vetores e 13 verificações na placa real.

### 4.1 Todos os requisitos da placa principal para o ID 200

| Item | Versão XL330 oficial (Dynamixel 2.0) | Nossa versão Feetech |
|---|---|---|
| Quando recebe uma solicitação | Uma `sync_read` a cada tick, IDs `[200, 20..24, 30..34, 10..14]`, endereço 124, tamanho 12 | A mesma `sync_read`, com 200 no início da lista; **endereço 56, tamanho 15** (mesmo endereço dos servos; a placa mapeia os dados da IMU para esse bloco) |
| Resposta | 12 bytes: `gyro x/y/z`, cada um i16 little-endian, faixa ±500 dps, 17,5 mdps/LSB; `quat x/y/z`, cada um em ponto flutuante IEEE de meia precisão; a placa principal calcula w | Os mesmos 12 bytes no início, seguidos por 3 bytes com contador de amostras e bits de estado, totalizando 15 |
| Se não responder | A `sync_read` aguarda todos os IDs; se um não responder, a transação inteira falha e **a placa principal fica sem dados de sensores naquele tick** | Igual |
| Outros comandos | Durante a execução, a placa principal só envia **sync_read**: `robotctl` não acessa o barramento e `missing_servos` / `check_registers` consultam somente os IDs dos 15 servos, não o ID 200 | Igual; PING / READ servem ao FD e ao URT-2 |
| Significado de zero | Quaternion totalmente 0 = SFLP ainda não produziu dados; a placa principal reutiliza o quadro anterior e não considera a IMU pronta | Igual |
| Orientação de montagem | `SflpDecoder::DEFAULT_MOUNT` = rotação de +90° em Y; tronco = `[+raw_z, +raw_y, −raw_x]` | A placa precisa ser instalada na mesma orientação do original; caso contrário, alterar o quaternion de montagem na placa principal |
| Prazo para produzir dados após ligar | A placa principal considera a IMU `ready` após 25 quaternions válidos; `decode` roda a cada tick, portanto **0,5 s a 50 Hz** | Igual |

Ponto essencial: **a placa principal nunca grava nem configura esta placa**. O comportamento pode ser fixado no firmware.

### 4.2 Módulos do firmware

```text
Firmware imu_to_dxl (STM32G031F8P6, 64 KB Flash / 8 KB RAM)
  ├ bus/        USART2 1 Mbps (PA2/PA3), DE por hardware (PA1, CR3.DEP=1 ativo em nível baixo), RX_EN (PB7)
  │   ├ rx      buffer circular DMA + interrupção de linha ociosa para separar pacotes
  │   ├ parser  detecção automática dos dois protocolos:
  │   │           FF FF FD 00 … CRC16  → Dynamixel 2.0
  │   │           FF FF ID LEN … CHK   → Feetech (LEN sempre ≥ 2, sem ambiguidade)
  │   │         fixa o protocolo após validar o primeiro pacote e não o destrava automaticamente em execução (ver complemento em §3.5)
  │   ├ handler PING → pacote de estado; READ / SYNC_READ → consulta a tabela de registradores; WRITE → aceita apenas o campo ID, reconhece os demais sem modificá-los
  │   └ tx      durante o envio, PB7 desativa a recepção (ou permanece ativo e descarta o eco pelo tamanho enviado); reativar no fim
  ├ imu/        LSM6DSV16X, SPI de quatro fios (PA4–PA7) + INT1 (PA0)
  │   ├ init    acelerômetro ±4 g, giroscópio ±500 dps, ODR 480 Hz; habilitar vetor Game Rotation SFLP a 120 Hz
  │   ├ isr     INT1 indica dados prontos → ler FIFO ou diretamente, obter gyro bruto + quaternion SFLP (o chip já fornece meia precisão)
  │   └ block   montar bloco de 12 bytes: gyro i16×3 + quaternion meia precisão ×3; substituir atomicamente (o barramento pode solicitar leitura a qualquer momento)
  ├ regs/       tabela de registradores: espelho de 128 bytes
  │              vista Dynamixel: 0 modelo (personalizado), 6 versão firmware, 7 ID (200), 8 baud rate, 124..135 bloco IMU, 136..143 diagnóstico
  │              vista Feetech:    3 modelo, 5 ID (200), 6 baud rate (0), 56..70 bloco IMU + contador + estado
  │              as duas vistas apontam para a mesma memória; somente os endereços diferem
  ├ clock/      HSI16 padrão; X1 está montado; após medir erros de comunicação, pode-se usar HSE bypass ou ajustar HSITRIM medindo o período do bit do controlador com timer
  └ diag/       log RTT (SWD do J3), contadores de pacotes recebidos, erros de checksum, respostas e timeouts
```

Requisito de temporização: a 1 Mbps, cada byte leva 10 µs. Como a placa fica primeiro na lista da `sync_read`, deve começar a responder **em menos de 100 µs** após receber a instrução (os servos Feetech levam cerca de 20–50 µs). A resposta tem 15 bytes de dados + cerca de 6 bytes de cabeçalho/final, total aproximado de 210 µs. Processar na interrupção; o loop principal não participa.

### 4.3 Ferramentas e validação

| Item | Escolha | Motivo |
|---|---|---|
| Linguagem | Rust `embassy-stm32` (ou C + STM32CubeG0 LL) | Mesma linguagem do runtime principal; é possível reutilizar o parser de pacotes do `rustypot` |
| Gravação / depuração | SWD pelo J3, `probe-rs` + CMSIS-DAP / ST-Link; logs por RTT ou printf pela USART1 nos pinos 4/5 do J3 | Nenhuma das opções interrompe a CPU; não usar semihosting, que para a CPU a cada printf |
| Testes unitários | Parser dos pacotes, dois checksums e mapeamento dos registradores executados no computador com `cargo test` | Não exige a placa |
| Bancada 1 | URT-2 + software FD; pesquisar e localizar ID 200; na página “Programação”, ler 56–70 e confirmar a variação dos dados da IMU | O FD já funciona como controlador Feetech |
| Bancada 2 | Placa + 15 servos ligados à placa principal; configurar `[bus] protocol = "feetech-sts"` em `robotd.toml` e verificar o item IMU de `robotctl health` | Combina os itens 9 e 10 da seção §5§ |

### 4.4 Qual opção fazer primeiro

A opção B (BNO085 ligado diretamente) não exige firmware e deve funcionar poucos dias após a chegada do módulo. A opção A exige escrever o firmware do zero; uma pessoa levaria de duas a três semanas para chegar ao teste no robô. **Fazer B primeiro para o pato conseguir levantar e, em paralelo, desenvolver A como versão definitiva**. Quando A estiver pronto, na placa principal será necessário apenas trocar um item de configuração; o código das duas opções permanece.

1. **Mapa dos registradores:** exportar os registradores 0–90 de um HD-1910 pela página “Programação” do FD, guardar no repositório e comparar linha a linha com §2: bits de status em 65, unidade de corrente em 69, unidade de aceleração em 41 e nível de resposta padrão em 8.
2. **Modo de operação:** o modo de fábrica 4 é o que precisamos? Qual é a diferença da resposta P/D entre os modos 4 e 0?
3. **Escrever P com lock ativo:** ao escrever 21 com `lock=1`, a resposta muda imediatamente? Após reiniciar, o valor volta? Isso determina qual plano usar em §3.3.
4. **Reinício 0x08:** testar em um servo reserva: após 1 s, ping responde, ID e EEPROM permanecem, 65 foi limpo, torque está desligado e o P escrito com lock ativo voltou ao valor EEPROM? Registrar as versões de firmware HD-1910 (endereços 0/1); confirmar se 0x08 funciona em todas as versões. O manual não esclarece. 0x0A já está definido como reset do contador de voltas; não precisa ser testado.
5. ~~Nível de resposta padrão 8~~ O manual indica valor inicial 1. Falta apenas confirmar que o FD não o alterou no HD-1910.
6. **Ordem de resposta em sync_read:** comportamento dos 15 servos quando um ID inexistente é colocado no início.
7. O bit 15 dos registradores de posição aparece no modo servo? E quais são os bits de sinal nos registradores de velocidade/corrente?
8. Convenção de direção (§3.7).
9. ~~Endianness~~ O manual indica little-endian na série magnética; END em 2 = 0 pode ser verificado durante a operação.
10. Opção B: jitter e perda de quadros do BNO085 a 100 Hz em I²C.
11. **Eco half-duplex:** a leitura do rustypot usa `read_exact` com tamanho fixo, sem buscar cabeçalho nem descartar eco. A HAT oficial usa buffer tri-state com comutação automática; com URT-2 ou adaptador ST/SC, se RX permanecer ligado, o primeiro pacote recebido em cada transação será a própria instrução e a transação inteira parecerá falhar. O sintoma pode ser confundido com fiação errada. Verificar primeiro na bancada, item 1b.
12. Alimentação da bancada: `battery_empty_shutdown` vem ativo e ordena sentar/desligar quando o barramento chega a 6,6 V ou menos. O HD-1910 também tem faixa de 6 V; manter a fonte acima de 7 V ou desativar essa opção inicialmente.
13. **Valor de fábrica da fase 18:** BIT2 (unidade de velocidade: 1 ou 50 passos/s), BIT3 (velocidade 0 significa parado ou máximo), BIT0/BIT7 (direção). Selecionar o fator de velocidade de §3.2 conforme esse valor.

## 8. Complementos após a revisão

### 8.1 Compilação e implantação

O fluxo oficial compila os artefatos do fork com `cargo board` / `xtask package` para gerar `.deb`. O `updater` instala somente pacotes assinados por chaves armazenadas em `/etc/robot/trusted_keys/`. O script `scripts/dev-push.sh` usa o fluxo de desenvolvimento, mas exige a chave privada `~/.duck-keys/team.dev.key`. O repositório contém apenas a chave pública `deploy/dev-key/team.dev.pub`; não temos acesso à chave privada da Pollen.

A solução é gerar um par de chaves, instalar a pública em `/etc/robot/trusted_keys/` na placa, habilitar `allow_dev_keys = true` e apontar `DUCK_DEV_SECRET_KEY` para a chave privada. Antes de escrever o código, é preciso comprovar que um `robotd` compilado localmente pode ser instalado e substituir a versão 0.13.0. Isso é pré-requisito para o item 9 da bancada.

### 8.2 Relação com a política e o treinamento

- As posições 20..34 do vetor de observação representam velocidades das articulações. Um erro constante na conversão da velocidade não gera erro na política, mas faz o robô andar mal. Aprovar primeiro o item 5 da bancada.
- `voltage_adapt` dimensiona as ações pela relação entre tensão e torque do XL330. Nos servos Feetech, desative inicialmente ou recalibre essa adaptação.
- O ONNX oficial foi treinado no XL330 (0,52 N·m), com orientação superior. O HD-1910 tem redução de 320:1 e torque de 1,47 N·m; sua dinâmica é diferente e provavelmente não conseguirá andar sem retreinamento. Os itens 0–9 da bancada verificam apenas a comunicação; o item 11 verifica se consegue ficar em pé. Para andar, será necessário retreinar.

### 8.3 Como as falhas aparecem em `robotctl health`

| Falha | Comportamento |
|---|---|
| Um servo não responde | A operação `sync_read` inteira falha; o barramento fica vermelho e mostra `missing N` |
| Sobrecarga ou superaquecimento bloqueado | O status 65 indica falha e a posição não acompanha o comando; recuperação em §3.4 |
| Gravação recusada pelo bloqueio da EEPROM | Na inicialização aparece `corrected`, mas a alteração não entra em vigor |
| Nível de resposta 0 | Cada gravação expira após 30 ms; `init` leva 1 s a mais e informa erro |
| Modo incorreto | A comunicação funciona, mas os comandos de posição não respondem ou o comportamento é inesperado |
| IMU congelada | 25 quadros idênticos geram `imu stale` e interrompem a detecção de queda |
| I²C travado (opção B) | A leitura da thread da IMU expira; o número de sequência para e o estado passa a `stale` |

### 8.4 Estratégia de testes

- Manter `FakeIo` inalterado e executar todos os testes existentes do upstream.
- Testar `bus_feetech.rs` sem a placa, usando quadros brutos gravados para verificar a decodificação em bloco (bits de sinal de posição, velocidade e corrente), `p_scale` e média de tensão.
- Executar `cargo test` no computador para testar o analisador de pacotes do firmware e suas duas rotinas de checksum.
- Antes de aplicar torque aos 15 servos pela primeira vez, reduzir `torque_limit` para 30 % no FD, habilitar a proteção contra sobrecorrente e fazer o teste com o robô suspenso.

### 8.5 Riscos determinantes (resolver estes quatro pontos antes de programar)

1. Usar o modo 4 ou o modo 0 (pendência 2).
2. O ganho fica na EEPROM; é possível gravá-lo com ela bloqueada? (pendência 3).
3. O comando REBOOT 0x08 funciona no firmware do HD-1910? (pendência 4).
4. Jitter de I²C na opção B (pendência 10).

## 9. Registro das revisões

### 2026-09-17 · Revisão independente por uma segunda instância do modelo

Comparação linha a linha com o código oficial `768e192`, rustypot 1.6.0, SDK Feetech de 2025-09-27 (`INST.h` / `SCS.h` / `SMS_STS.h`) e manual do protocolo V1.01. Foram corrigidos: `gain` é 200, não 160; o modo de operação de fábrica é 4, não 0; os significados de 0x06 / 0x0A estavam invertidos; os registradores de ganho ficam na EEPROM; `ready` é 0,5 s a 50 Hz; são 23 crates; `Box<dyn RobotIo>` não compila, por isso foi substituído por um enum; havia dois valores inconsistentes na configuração de `imu`; `robotctl` não acessa o barramento. Foram acrescentadas as observações sobre as duas opções em §3.5, as pendências 5–10 em §6 e toda a seção §8.

### 2026-09-17 · Segunda rodada de revisão

Uma nova instância do mesmo modelo verificou somente as alterações da primeira rodada, confirmou todas e fez novos ajustes: o manual do codificador magnético de 2024 define 0x0A como “reiniciar o contador de voltas do servo”, não como REBOOT; a implementação de `reboot` agora termina com torque 0, conforme o contrato de `io.rs`; o significado de `lock=1` é citado conforme o manual (“não é salvo após desligar”); a opção `--protocol` foi unificada com a chave `[bus] protocol`; §8.1 recebeu instruções sobre chaves autoassinadas; foram adicionadas as pendências sobre eco half-duplex (11) e desligamento da fonte da bancada (12); também foram ajustadas as expressões `imu_stale`, RK3566 e a citação em §1.2.

### 2026-09-17 · Comparação com os documentos mais recentes do site oficial Feetech

O usuário forneceu a página de documentos `doc.feetech.cn`. Foram obtidos os documentos oficiais Feetech de 2026: “SCS Communication Protocol” v1.0 (2026-06-09) e “Magnetic Encoder STS Memory Table Manual” v1.1 (2026-08-27); as cópias estão em [`docs/飞特资料/`](../docs/飞特资料/). Correções: **a Feetech tem o comando REBOOT (0x08, cerca de 800 ms; primeiro desligar o torque)**, e a seção §3.4 foi reescrita; a descrição de `reboot-motors` não precisou ser alterada; 0x06 restaura parâmetros (com backup por 0x09), não a configuração de fábrica; o manual confirma que `lock=1` não salva após desligar; o nível de resposta padrão é 1; a ordem dos bytes é little-endian (registrador END); foram esclarecidos os bits de status 65, a unidade de corrente de 6,5 mA, a unidade de velocidade determinada por BIT2 da fase e o modo de torque 2 como amortecimento. O endereço 7 da tabela STS genérica está reservado, portanto deixou de ser tratado como confirmado. As pendências 4/5/9 foram atualizadas.

### 2026-09-17 · Terceira rodada de revisão

Foram completadas as alterações de 0x08 que faltavam nas linhas de `robotctl` em §3.1 e de `adopt` em §3.6. Também foram corrigidos estes pontos: 0x08 não precisa ser enviado como pacote bruto, pois rustypot v1 já oferece `Reboot`; `reboot()` não pode esperar 1 s dentro do ciclo de controle, pois chamadas sequenciais para 15 servos bloqueariam o ciclo por 15 s. A espera foi movida para `adopt`, e `REBOOT_SETTLE` para Feetech deve ser de pelo menos 1 s; a afirmação de que o valor de P gravado com o bloqueio ativo volta ao valor da EEPROM depois de reiniciar foi rebaixada a hipótese. Novas observações: a fase 18 determina a unidade da velocidade, o significado de velocidade 0 e a direção; deve ser lida na inicialização (pendência 13); os registradores 41/46 não devem ser escritos na inicialização; o modo de amortecimento não substitui Limp; a área EEPROM é 5–39; o manual não informa os valores de fábrica de P/D nem os bits de sinal da corrente.

## 10. Andamento da implementação

### 2026-09-18 · Primeira versão: `FeetechIo` e seleção de protocolo

Na branch [`feetech` do fork](https://github.com/fanhao375/microduck/tree/feetech) (`8db8f00`, rebaseada para o upstream 0.14.1 em 2026-09-20), as alterações ficaram restritas aos pontos listados em §3.1. Os valores padrão não mudaram; sem `[bus] protocol`, o comportamento permanece igual ao anterior.

| Arquivo | Alterações |
|---|---|
| `duck-control/src/bus_feetech.rs` (novo) | `FeetechIo`: uma chamada `sync_read` por ciclo, no endereço 56 e com tamanho 15 (posição, velocidade, carga, tensão, temperatura, status e corrente); tensão e temperatura ficam em cache, sem transação adicional em `slow_sensors`; a posição-alvo é convertida conforme a direção da articulação e escrita diretamente em 42, limitada a 0–4095; `set_gain` grava apenas P, sem desbloquear (a gravação entra em vigor, mas não é persistida após desligar), preservando D/I de fábrica; `reboot` desliga o torque antes de enviar 0x08 e não espera dentro do ciclo de controle; na inicialização verifica END=0 e nível de resposta=1 (qualquer outro valor gera erro), apenas avisa se o modo não for 4 e lê a fase para determinar a unidade de velocidade; troca do servo: desbloquear, gravar o ID, bloquear, reiniciar e testar o novo ID com ping |
| `duck-control/src/bus_select.rs` (novo) | Enum `AnyBus` para selecionar um de dois backends, em vez de `Box<dyn RobotIo>`, que não compila |
| `robotd-params` | `[bus] protocol = "dynamixel2" \| "feetech-sts"` e `[bus.feetech] p_scale / directions`, registrados na tabela de parâmetros e visíveis em `robotctl configure` |
| `robotd/src/main.rs` | `BusIo` substituído por `AnyBus`; a abertura do barramento recebe o protocolo. Parâmetros inválidos (direção diferente de ±1 ou número incorreto de entradas) geram erro direto, sem nova tentativa |
| `deploy/robotd.toml` | Duas novas chaves, ainda comentadas |

**Ainda não implementado**: IMU. Neste backend, `imu_ready()` sempre retorna false; por isso, o daemon não inicia a política nem a detecção de queda. Ainda assim, `robot init` (interpolação de 2 s até a pose em pé) continua disponível, como convém à primeira etapa de validação. Adicionar `imu_source` quando o BNO085 chegar.

**Validação registrada à época**: os testes dos três crates foram executados no WSL: 80 no controle, 150 nos parâmetros e 93 no daemon, todos aprovados. Foram adicionados 11 testes para conversão de posição, espelhamento de direção, limitação de valores, sinal do 15º bit, decodificação do bloco, unidade da velocidade, mapeamento de ganho e validação de parâmetros. `cargo fmt --check` e `cargo clippy -D warnings` não apontaram problemas. ### 2026-09-20 · Alinhamento com o upstream 0.14.1

O upstream lançou as versões 0.14.0 e 0.14.1 em 16–17 de setembro; a branch foi rebaseada sem conflitos. Entre esses 55 commits, não houve alterações em `duck-control/`, `robotd-params/` ou na definição do protocolo. Apenas uma flag de estado `sitting` foi acrescentada em `robotd/src/main.rs` (há duas situações para “levantar”: quando está em pé, usar `robot.init`; quando está sentado, usar `robot.do sit_toggle`. O cliente precisa saber em qual delas está), sem conflito com as linhas em que `BusIo` foi substituído.

As principais mudanças do upstream foram o aplicativo móvel (o `btd` ganhou rotas para executar `init` / `enable` pelo telefone), o playground web para crianças (um truque por cartão), a tipagem das especificações de políticas e a remoção de `fake_duck.py`. Em vez de manter um pato falso separado para simulação, o próprio código do robô passa a servir como gêmeo digital. Essas mudanças ficam fora da área de integração deste fork, mas o estado `sitting` poderá ser útil ao desenvolver uma interface de controle.

**Etapas na placa superior** (após ligar a placa):

1. Confiar na chave pública de desenvolvimento na placa: `/etc/robot/trusted_keys/replica.dev.pub`; definir `allow_dev_keys = true` em `/etc/robot/updater.toml`. A atualização não sobrescreve esse arquivo; nas máquinas de produção, essa opção fica desativada.
2. Instalar pelo atualizador da placa (`robotctl update apply daemon --from`), que executa uma verificação de integridade e reverte automaticamente para 0.13.0 caso a inicialização falhe. Nesta etapa, manter `robotd.toml` em `dynamixel2` para primeiro validar o fluxo de implantação.
3. Alterar `robotd.toml`: definir `port = "/dev/ttyUSB0"` (URT-2 conectado à placa), `protocol = "feetech-sts"` e `[bus.feetech] directions`. A bancada web confirmou individualmente que os 15 servos usam −1: a direção em que a leitura do HD-1910 aumenta é oposta à do XL330. A página oferece “Copiar tabela de direções do robotd” para gerar essa linha. Reiniciar `robotd` e verificar a seção do barramento em `robotctl health`.
4. Suspender o pato e executar `robotctl robot init`.
