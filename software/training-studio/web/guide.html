训练自己的动作：从想法到可验证的策略

适用：HD1910 Microduck · 核对日期：2026-10-23

1. 先确认目前能做什么

当前训练台只有「HD1910 平地行走」和「HD1910 起伏地形行走」。单腿站立、跳跃、自定义转圈尚未接入。 改实验名称不会改变动作目标，需要先在训练引擎中开发任务。

官方项目用 PPO 强化学习训练策略，再导出 ONNX 供机器人运行。官方项目说明

想做的动作 当前状态与可借鉴内容
单腿站立 需要新增 HD1910 任务；可参考站姿与坐站任务的控制结构
跳跃 需要新增任务，并先验证舵机与机器人是否具备条件
普通慢速转向 成熟行走策略可接收前进、横移和转向速度命令
转满 360° 后停下 需要累计转角、停止条件与完成判定

官方有 SitStand、StandUp、BallKick、Roulade 等任务，但这些上游配方面向 XL330，移植到本机需要 HD1910 适配。官方 Spin 使用轮滑模型，不能直接用于当前脚掌；以官方任务注册表为准。

2. 训练到底在训练什么

你先说明“什么算成功”，开发者把它变成可测量的目标、奖励、失败终止和难度阶段。PPO 在大量仿真尝试中寻找关节控制方法。例如，奖励抬起指定脚并站稳，惩罚支撑脚滑动，身体触地则结束这一轮。

奖励写得不完整，机器人可能找到“得分很高但动作不对”的办法，因此还要用接触、姿态和时间条件验收。关键帧可以帮助描述动作或检查姿态，但不是本流程的关节轨迹播放器；当前训练台也没有上传视频后自动模仿的功能。

官方的新环境流程强调：复用相近模板、先验证物理条件，再做配置测试和短试跑。官方开发指南

3. 先写一张动作需求单

先用下面这段描述交给开发者或代码助手，即可开始设计任务：

为我的 HD1910 小鸭开发单腿站立任务。起点是双脚稳定站立，左脚支撑，右脚离地，保持后回到双脚站立。初步希望离地 2 厘米、保持 3 秒；数值先做仿真可行性验证。禁止头部或躯干撑地，限制倾斜和支撑脚滑动。先交付任务配置、CPU 测试与短试跑方案，再提供多次评估的视频和成功率。接入训练台时使用独立实验目录。

其他动作同样写清：机器人配置、起点、动作顺序、终点、允许接触的部位、持续时间，以及失败条件。视频可作为意图参考；验收条件仍需转成仿真可测量的数据。

4. 单腿站立：建议怎样拆

以下是建议配方，尚未实现，也未验证可行。 初始设想是：双脚站立 → 向左移重心 → 右脚离地约 2 厘米 → 保持约 3 秒 → 回到双脚。这里的阶段描述任务进度，不要求逐帧照抄关节角度。

先验证移重心后左脚能否独立承重，再从低抬脚、短保持开始。稳定后逐步增加高度、保持时间、初始姿态扰动和轻微外力。不能一开始同时要求高抬腿、长时间保持和强抗推。

成功判定必须同时满足：指定左脚承重；右脚达到目标离地高度；保持期间无头部、躯干接触；倾角与支撑脚滑移低于明确且有限的阈值；最后恢复双脚稳定支撑。阈值应根据模型测量确定，不能只看躯干高度就判定站稳。

奖励可分别反映重心转移、抬脚高度、稳定保持和返回完成。脚尖偶然离地或倒下后脚悬空均不能计为成功。只训练左脚支撑时，不应启用左右镜像损失；只有左右目标命令也正确镜像、任务确实对称时，才考虑这种训练约束。

5. 跳跃与转圈：分别处理

跳跃建议先做物理评估。 检查实际质量与惯量、关节行程、舵机扭矩和速度、供电压降、控制延迟及足地接触模型。若瞬时输出不足，增加训练轮数不能解决。当前参数只是仿真基线，不能承诺实机一定跳得起来。

通过评估后，可把目标拆成蓄力、双脚离地、落地和重新站稳。验收应同时记录真实离地、起跳方向、落地冲击和落地后的稳定性；只有腾空奖励容易鼓励翻倒。难度从很小的离地动作逐渐提高。

转圈先分清需求。 普通原地转向可尝试成熟行走策略的 vx=0、vy=0、vyaw≠0 命令，并验证停止命令下的表现。若要精准转满一圈，应记录连续累计偏航角；仅比较首尾朝向分不清“没转”和“转了一圈”。建议任务同时约束目标转角、中心漂移、倾斜及结束时角速度，转到后需停稳。

6. 从需求到策略的七步

  1. 测物理条件。 检查模型、接触和执行器；从略有扰动的初始姿态验证目标姿势，测量高度、倾角与滑移。
  2. 选最接近的模板。 从本地 HD1910 配置保留执行器与接口，再借鉴相关上游任务；检查碰撞模型是否能观测到要求禁止的身体接触。
  3. 写任务规则。 实现命令、初始状态、奖励、失败终止和逐步加难的课程；为新任务分配独立实验名。
  4. 先做 CPU 配置测试。 核对关节映射、观测维度、奖励正负号、接触条件与阶段切换；它不替代真实仿真步进。
  5. 做 64 环境、5 轮短试跑。 检查加载、数值有限、奖励计算、保存和导出链路。通过只说明链路可用。
  6. 分阶段训练与评估。 每阶段选检查点，结合视频、成功次数／总次数、跌倒率和动作误差决定是否加难；保留固定测试条件和随机种子。
  7. 导出并验证部署。 核对归一化、输入输出和关节顺序，先做仿真部署测试，再按实机校准与受控试验流程验证。

当前训练台一次检查点评估固定为 250 步，约 5 秒。自定义动作如果包含较长的进入、保持和退出过程，开发者需延长评估并覆盖完整动作周期，再以多次不同初始状态测试统计成功率。单段短回放不能代替这些验收。

7. 现在能运行的命令

以下仅针对已经准备好依赖的 Linux／WSL2 环境，在 software/training/ 目录执行。第二条会实际占用 GPU，训练的是现有平地行走任务。

uv run --frozen list-envs

uv run --frozen train Mjlab-Velocity-Flat-MicroDuck-HD1910 \
  --env.scene.num-envs 64 --agent.max-iterations 5 \
  --agent.logger tensorboard --agent.run-name hd1910_m6_smoke

单腿站立或跳跃必须等新任务实现、注册并测试后，才能使用它的真实任务 ID。当前也可在训练台选择现有配方完成短试跑，熟悉记录、评估和导出过程。

8. 开发者需要改哪些地方

以下路径相对于 software/training/：

文件 工作内容
src/mjlab_microduck/tasks/microduck_hd1910_env_cfg.py 参考 HD1910 执行器接入方式，避免回退成 XL330
src/mjlab_microduck/tasks/microduck_*_env_cfg.py 新增任务配置、课程和独立实验名
src/mjlab_microduck/tasks/mdp.py 实现奖励、命令、观察、事件及成功判定
src/mjlab_microduck/tasks/__init__.py 注册真实任务及评估配置
tests/ 验证配置、不合法状态及奖励条件

训练台还需修改 software/training-studio/training_studio/config.py 的配方白名单，并调整 commands.py、service.py 的日志和检查点路径。目前 EXPERIMENT 固定为 microduck_hd1910_velocity，应改为按配方解析并校验，覆盖训练、续训、评估和导出；只加一张网页卡片不够。

本地接口基线为 61 维观测、14 维动作、50 Hz。导出应走现有 scripts/export.py，保留观测归一化。新任务若重新解释命令槽位，部署端必须同步写入正确命令；若改维度，则需同步修改运行时并重新验证兼容性。

本地 UPSTREAM.md 记录的上游基线为 d424a0c…，依赖锁定 mjlab 1.3.0。官网 develop 会继续变化，最新发布命令和示例名称不代表本地已支持；开发时应以本地源码与 list-envs 输出为准。

说明基于本仓库冻结训练环境。新增动作须完成适配与验证后才能加入训练配方。
